## Система маркировки доверия

sharkfin размечает факты тремя маркерами, и эта разметка — самое ценное в документе, потому что она прямо отображается в нашу модель `origin` (`spec.md` § Domain rules):

| Маркер sharkfin | Значение | Наш `origin` |
|---|---|---|
| `[HW]` | round-trip выполнен на физическом устройстве (базовая плата — Attack Shark X86, в их реестре device 1967) | `Verified(hw)` — но **только для той платы, на которой это делали**, не для семейства |
| `[FW]` | вычитано из дампа прошивки, с указанием образа там, где это существенно | `FromFirmware` |
| `[JS]` | только из вендорского хост-кода, ни разу не исполнялось на устройстве | `FromVendorJs` |

При переносе в `data/protocols/royuan.yaml` (TICKET-09/10) маркер источника обязан сохраниться per-opcode. Факт `[JS]` не даёт права на запись — по нашему правилу запись требует `confidence >= Verified` для конкретного семейства.

## Транспорт

| Параметр | Значение | Маркер |
|---|---|---|
| Usage page | `0xFFFF` (vendor-defined) | `[HW]` |
| Usage | `2` | `[HW]` |
| Тип репортов | Feature reports (в обе стороны) | `[HW]` |
| Report ID | `0` в обе стороны | `[HW]` |
| Размер пакета | 64 байта | `[HW]` |
| Задержка «запрос → ответ» | ~10 мс | `[HW]` |
| Канал | только проводной USB — беспроводные подключения этот слой не отдают | — |

**Известные VID семейства:** `0x3151` (основной), `0x379a`, `0x374a`, `0x38a9`, `0x046a`, `0x2ea8`, `0x145f`.

**Поведение ответа:** на GET-операциях устройство эхом возвращает опкод в байте 0. Исключение — постраничное чтение больших блоков (keymatrix, macro, userpic): там ответ содержит сырые данные страницы без эха опкода. Практическое следствие для нашего `verify()`: «пришёл ответ с нужным опкодом в байте 0» — это **не** подтверждение записи, это подтверждение того, что устройство поняло формат кадра. Для bulk-чтений даже этого признака нет.

## Семейства протокола и как определяется принадлежность

sharkfin определяет: `yc500`, `gen2`, и внутри gen2 — под-линии по разбору кадров дисплея: `yc3121`, `yc3123`, `ry5088`. Тестовая плата с маркером `[HW]` — Attack Shark `X86`.

**Правило назначения семейства: только по реестру, никогда по product ID.** Это независимое внешнее подтверждение нашего доменного правила «PID переиспользуется вендорами, семейство не выводится из VID:PID» (`spec.md` § Domain rules) и нашего FR4. Причём подтверждение сильное: проект, покрывающий 945 из 949 плат, пришёл к тому же выводу эмпирически.

Масштаб реестра sharkfin (для калибровки наших ожиданий по `pregistry`): 949 плат всего, из них 288 с боковой подсветкой, 172 с экраном (152 gen2 + 20 yc500), 25 различных размеров экрана.

## Контрольные суммы

Два варианта, различаются только шириной покрытия и позицией байта:

- **Bit7:** сумма байтов 0–6, результат `0xFF - (сумма & 0xFF)`, кладётся в байт 7.
- **Bit8:** сумма байтов 0–7, тот же инвертированный результат, кладётся в байт 8. Используется опкодами параметров подсветки (`SET_LEDPARAM` `0x07`, `SET_SLEDPARAM` `0x08`).

Для под-линии yc3123 (экранные кадры) действует та же схема, но пакет индексируется от смещения буфера −2 — т.е. при переносе кода на эту под-линию границы суммирования смещаются. Маркер: `[HW]` для самих контрольных сумм.

Практическое следствие: контрольная сумма — свойство **опкода**, не семейства. В `pproto` кодек обязан выбирать вариант по опкоду, а не по устройству; иначе LED-опкоды посчитаются неверно. Это же — готовый property-тест (`encode(decode(x)) == x` + проверка суммы, `spec.md` § Test seams).

Обратить внимание на **пересечение номеров с разной семантикой между семействами**: `0x06` — это Options у yc500, но Debounce у gen2; `0x09` — Keymatrix у yc500, но Options у gen2; `0x11` — Debounce у yc500, но таймеры сна у gen2. Это не абстрактный риск из нашего плана, а задокументированный факт: тот же байт пишет разные подсистемы в зависимости от семейства. Отсюда же следует, что `opcode_acl` в реестре (`spec.md` Приложение B) обязан быть **per-family**, что схема и предусматривает — подтверждено внешними данными.

### Ответ на X86 (`[HW]`): что отвечает, а что нет

**Отвечают** (все — GET/чтение): `0x80`, `0x85`, `0x86`, `0x87`, `0x88`, `0x89`, `0x8B`, `0x8C`, `0x8F`, `0x90`, `0x91`, `0x92`, `0x97`.

**Не отвечают:**
- `0x1B`, `0x1C`, `0x1D`, `0x1E` — магнитные переключатели (HE);
- `0x65`, `0x9C`, `0x9D`, `0x9E` — Rapid Trigger;
- `0xE5` — gen2 отклоняет явно;
- `0x22`–`0x32` — экран/картинки на части плат;
- `0x40`, `0x41` — бутлоадер;
- `0xA5`–`0xAE`, `0xB0`–`0xB2` — экран;
- `0xAE`, `0xC0`, `0xC1` — MLED (gen2 отклоняет явно).

## HE-специфичный слой — центральный вывод этого конспекта

Это и есть та причина, по которой существует наш проект, поэтому вывод формулируется отдельно и явно.

**Факт 1.** В OEM-протоколе есть выделенный блок опкодов под HE: `0x1B`–`0x1E` (магнитные переключатели) и `0x65`, `0x9C`–`0x9E` (Rapid Trigger). Источник: sharkfin `docs/PROTOCOL.md` @ `d657f19`.

**Факт 2.** На плате Attack Shark X86 ни один из этих опкодов не отвечает — маркер `[HW]`, то есть это результат реальной попытки, а не предположение.

**Факт 3.** На плате Attack Shark X68 PRO HE (Sonix, VID `0x3151` / PID `0x5030`) опкод `0x1B` **работает** и включает поток аналоговых значений хода клавиш. Источник: `he-analog-gamepad`, прочитано 2026-08-17.

**Вывод (мой, не из источников).** «Не отвечает» на одной плате семейства — **не доказательство отсутствия HE-функциональности в семействе**; это доказательство того, что прошивка конкретной платы этот блок не реализует. Наша модель `origin` уже умеет выражать разницу между «проверено на плате X» и «свойство семейства» — и вот конкретный случай, когда смешение этих двух уровней привело бы к неверному выводу «у ROYUAN нет HE-протокола».

Это же уточняет наше доменное правило. В `spec.md` записано «ответ устройства — не доказательство» (устройство может соврать успехом). Обратная сторона симметрична и должна быть записана так же явно: **отсутствие ответа — не доказательство отсутствия возможности**, оно доказывает только отсутствие возможности на этой прошивке этой платы. Анти-фикция-фильтр Learning Mode (FR5) понижает гипотезу — и правильно, что понижает, а не отбрасывает.

### Аналоговый стрим (Attack Shark X68 PRO HE, `he-analog-gamepad`)

| Параметр | Значение |
|---|---|
| VID / PID | `0x3151` / `0x5030`, контроллер Sonix |
| Где читается | отдельный vendor-specific интерфейс (в проекте — интерфейс 2, `mi_02`), **не** клавиатурная коллекция |
| Включение | HID Feature Report: `[0x1B, 0x01, 0x00, …]`, добит нулями до 64 байт |
| Выключение | `[0x1B, 0x00, 0x00, …]`, добит нулями до 64 байт |
| Формат репорта стрима | Report ID `0x05`; байт 1 — префикс `0x1B`; байты 2–3 — аналоговое значение `u16` LE; байт 4 — идентификатор клавиши |
| Диапазон значений | 0 (отпущена) … ≈350 (нажата до упора) |
| Происхождение фактов | реверс USB-трафика и разбор HID-дескрипторов, не документация вендора → по нашей шкале ближе к `[JS]`/`FromVendorJs`, чем к `Verified(hw)` |

Следствия, важные для наших тикетов:

1. **Размер пакета включения совпадает с sharkfin (64 байта), и префикс `0x1B` — тот же байт, что у sharkfin числится опкодом магнитных переключателей.** Это сильный аргумент, что это один и тот же протокол, а не два разных. Гипотеза, не факт: проверяется в TICKET-09.
2. **Открытый вопрос, который нужно закрыть эмпирически:** тот же ли это vendor-TLC, что описан у sharkfin (usage page `0xFFFF`, usage `2`, report ID `0`), или отдельная коллекция? sharkfin описывает конфигурационный канал через feature reports с report ID `0`; аналоговый стрим приходит как репорт с ID `0x05`. Совпадают ли они на уровне интерфейса — по имеющимся данным **неизвестно**. Это конкретный, проверяемый вопрос для HID-инвентаря (TICKET-08/09), и он прямо влияет на `spec.md` Q2 и на то, останется ли Analog Monitor флагманской фичей v1.
3. **Диапазон ≈0…350 — не нормализованный и не в миллиметрах.** Наша capability `he.analog_stream` объявлена как нормализованный ход 0..1 (`spec.md` Приложение A), значит для этого семейства нужен масштабирующий коэффициент в `quirks`, а не хардкод. Верхняя граница «примерно 350» — сама по себе не проверенный факт (в источнике она приблизительная), калибровать на железе.
4. **Включение стрима — это запись** (Feature Report), а не чтение. Значит даже «read-only демо-фича» Analog Monitor проходит через `psafety`/`SafeCommandId` и не может быть исключением из FR2. Учесть при декомпозиции TICKET-15.

## Деструктивные опкоды — не отправлять никогда

Наш глобальный запрет («никакой прошивки в v1», `SafeCommandId` не транслирует класс `destructive`) означает, что этот список нужен не для реализации, а чтобы гарантированно **не сгенерировать** такую команду случайно.

| Опкод | Что делает | Заметки |
|---|---|---|
| `0xAC` | стирает flash-чип | ~55 с на gen2; на yc3123 дополнительно выставляет бит 0 по `0x20166`; предзагружает ответ `AA AA 55 55`. Трактуется как стирание flash **в обоих семействах** |
| `0x30` / `0x31` | вход в бутлоадер (boot logo, yc500) | — |
| `0x40` / `0x41` | вход в бутлоадер | на X86 не отвечают |
| `0x02` (yc500) / `0x01` (gen2) | factory reset | не стирает flash, но сбрасывает пользовательскую конфигурацию; **номера меняются между семействами** → отправка не тому семейству = неизвестная команда |

⚠️ Отдельно зафиксировано в источнике и подтверждает наш архитектурный gate: **ни один из этих опкодов не может быть отправлен «слепо»**, потому что номера перекрываются между семействами. У нас это выражается сильнее: в production-сборке они не переводятся в исполняемую команду вообще, независимо от того, что скажет UI или пользователь.

Для `data/protocols/royuan.yaml` (TICKET-09/10): все перечисленные опкоды заносятся с классом `destructive`; всё, что не перечислено явно как безопасное, — класс `unknown`, то есть запрещено по умолчанию.

| Интервал между страницами (yc500) | 40–100 мс | — |
| Загрузка пользовательской картинки | 2 загрузки / 10 с, страницы через 100 мс, 2 с settle | — |
| ry5088 | если предыдущая страница ещё передаётся, новая **молча отбрасывается** (busy-бит) | — |

**Что происходит при нарушении:** слишком частые загрузки приводят к застреванию endpoint'а с ошибками протокола. Это ровно тот сценарий, который у нас описан как failure mode «config-endpoint не отвечает после серии flash-записей (stall) → понятная ошибка "переподключи кабель"» (`spec.md` § Failure and fallback behavior) — теперь он подтверждён внешним источником с маркером `[HW]`, а не является нашим предположением.

Прямое следствие для `psafety`: rate limiter заполняется для ROYUAN этими измеренными значениями (`quirks`), а не глобальной константой — как и записано в доменном правиле. Значения выше — стартовая точка для семейства ROYUAN; для нового/неизвестного семейства правило остаётся «одна запись за раз с подтверждением пользователя».

## Форматы данных, которые понадобятся при реализации

Зафиксировано, чтобы TICKET-09 не пришлось возвращаться к sharkfin.

**Значение слота раскладки — 4 байта, тип в байте 0:**

| Тип | Смысл | Разметка |
|---|---|---|
| `0x00` | HID usage | `[0, usage, 0]`; комбинации — в байтах 1 и 3 |
| `0x01` | кнопка мыши | — |
| `0x03` | consumer usage | `[0, младший, старший]`; например Vol+ = `[3, 0, 0xE9, 0]` |
| `0x09` | макрос | `[режим, индекс, 0]`; режимы: 0 повтор, 1 переключение, 2 удержание |
| `0x0A` | специальные | `[1,0,0]` = Fn, `[12,0,0]` = энергосбережение |
| все нули | на Fn-слое — проваливается на базовый слой; на базовом слое — «мёртвая» клавиша | важный кейс: «нули» здесь **не** означают «не задано» |

Последняя строка — прямая иллюстрация нашего принципа «не превращать unknown в ноль/пусто»: в этом протоколе нулевой слот имеет два разных определённых смысла в зависимости от слоя, и ни один из них не равен «значение отсутствует».

**Объёмы:** раскладка — 128 слотов × 4 байта = 512 байт на слой; макросы — 50 слотов × 256 байт; пользовательская картинка — 384 байта (128 × RGB); банки постраничной передачи (yc3123/ry5088) — 10 × 4096 байт.

**Кадр записи макроса** (`0x16` у yc500 / `0x0B` у gen2): байт 0 — опкод, байт 1 — слот, байт 2 — страница, байт 3 — `56` (длина порции), байт 4 — `1` только на последней странице (флаг commit), байты 8–63 — 56 байт данных с добивкой нулями.

**Тело макроса:** счётчик повторов `u16` LE, затем поток пар «событие/задержка»: клавиша/кнопка — `[код, нажатие<<7 | задержка]` либо `[код, нажатие ? 0x80 : 0, задержка u16 LE]` при задержке >127 мс или нулевой; перемещение мыши — `[0xF9, задержка, dx i8, dy i8]`; кнопки мыши — `0xF0`–`0xF4`; коды клавиш — HID usage `0x04`–`0xEF`. Терминатор — четыре нулевых байта.

**LED-параметры (Bit8):** `[опкод, mode, 5−speed, brightness, (option<<4)|флаги, R, G, B, ck8]`. Скорость инвертируется: UI 0–4 → провод 5–1. Яркость 0–4 напрямую. Ниббл флагов: `7` — фиксированный цвет, `8` — радуга (режимы 22/23 инвертируют, режим 13 принудительно делает cyan, режим 21 обнуляет байт). Белый `0xFFFFFF` передаётся как `0xFAFAFA`. При GET флаги 0–6 переопределяют RGB на red/orange/yellow/green/cyan/blue/magenta. RGB ниже `0x080808` не светится — для выключения использовать опцию backlight off, а не тёмный цвет. Режимы подсветки: 1–19, 21–23 (основные), 0–5 и 20–22 (боковая).

Эти «мелочи» (инверсия скорости, подмена белого, порог `0x080808`) — типичные `quirk`-записи, и они же объясняют, почему в схеме реестра у `quirk` есть поле `reason`: без причины такая запись через полгода выглядит как случайная магия.

## Чего в конспекте нет

- Не читались `docs/BOARDS.md` и исходники sharkfin построчно — для целей TICKET-01 (дать TICKET-09 возможность начать Safe Probe) достаточно `PROTOCOL.md`; таблица VID:PID по 949 платам будет нужна в TICKET-05 (OEM-карта), и брать её надо будет как данные с проверкой лицензии на **данные**, а не как факты протокола.
- Не выяснено, какие именно опкоды считаются безопасными для probe **на других платах** семейства, кроме X86 — по определению эмпирический вопрос TICKET-09.
- Не выяснена семантика битов Options у gen2 (в источнике прямо сказано, что значения не установлены). Для нас это значит: класс `unknown` → запись запрещена, чтение допустимо.
- Беспроводной канал (BT/2.4G) конфигурационный слой не отдаёт — соответственно `dev.power.battery` через этот протокол недостижим, что совпадает с уже зафиксированным Q3 в `spec.md`.
