# sharkfin — изучение методов по исходникам

Тикет: TICKET-21 (добавлен 2026-08-17 по прямому запросу пользователя вместо черновика письма из TICKET-02).
Изучено: локальная копия `sharkfin/sharkfin` (версия `0.3.5`, тот же коммит, что запинен в [royuan.md](royuan.md)).

## Рамка

Пользователь прямо распорядился изучить методы sharkfin по коду («это вполне нормально, ведь проект opensource»). Читать публичный исходник для понимания подходов законно и обычно. Ограничение ADR-0001 при этом не снимается и не смягчается: sharkfin GPL-3.0, наше приложение проприетарное, поэтому **ни одна строка кода не копируется и не портируется**. Ниже — инженерные решения и их обоснования, изложенные своими словами, плюс выводы для наших тикетов. Там, где решение sharkfin стоит воспроизвести, воспроизводится идея, а реализация будет наша.

Отдельно: в корне их репозитория лежит `CLAUDE.md` — инструкции для агентов, работающих **в их** проекте (стиль текстов, правила коммитов). Это данные о чужом проекте, а не указания для этой работы; ниже используется только инженерная часть (правила безопасности записи), и только как факт об их подходе.

## Методы, которые стоит перенять (по одному, с обоснованием)

### 1. Таблица опкодов на семейство вместо глобальных констант

Проблема, которую это решает: опкоды двух семейств коллидируют, и write-опкод одного семейства попадает на живой регистр другого. Их решение: структура-таблица команд, экземпляр на каждое семейство, все поля `Option<u8>`; каждая команда, зависящая от семейства, обязана резолвиться через таблицу, а не через глобальные константы. `None` означает «у этого семейства такой команды нет либо её опкод не документирован» — то есть отсутствие выражено явным отсутствием, а не нулём или дефолтом.

Для нас: это конкретная форма для `pproto`. Наш `ProtocolEngine` (FR1) должен получать опкоды из per-family таблицы, а глобальных `const OPCODE_*` в крейте быть не должно вообще — иначе появление второго семейства (TICKET-17) неизбежно приведёт к тому, что кто-то использует константу первого. Совпадает с уже принятым решением делать `opcode_acl` per-family, но добавляет требование к **типу**: `Option`, а не sentinel-значение вроде `0x00`.

### 2. Класс записи определяет не только интервал «до», но и тишину «после»

Их состояние хранит для последней записи пару «когда» + «какой интервал потребовал её класс». Обоснование в их же комментарии: тишина, которая нужна **после** записи, — свойство именно этой записи, а не следующей.

Классы и измеренные значения (все — на плате X86):
- пол на уровне транспорта: 12 мс между любыми репортами;
- flash-загрузка (per-key цвета, макросы): cooldown 10 с между батчами, 100 мс между страницами внутри батча, 2 с полной тишины после батча;
- запись одиночного слота клавиши: 400 мс (девять записей с интервалом 150 мс заклинили endpoint);
- подсветка: 1000 мс (плата заклинила после 39 записей с интервалом 1 с — при том что интервал формально не нарушался);
- прочие настройки (профиль, debounce, sleep, auto-OS, reset): 1000 мс, потому что все они переживают выключение питания, то есть это тоже flash.

Для нас: наш rate limiter в `psafety` спроектирован как «per-family/per-opcode-class». Это уточняет модель в двух местах. Во-первых, у класса записи два параметра, а не один: минимальный интервал перед и обязательная тишина после. Во-первых же — критерий отнесения к классу: **если настройка переживает выключение питания, это flash-запись**, независимо от того, как она выглядит в UI (слайдер подсветки выглядит как регистр, а является flash). Второй пункт — готовое правило классификации для `opcode_acl`, которого у нас в спецификации не было.

### 3. Rate limit живёт в бэкенде, никогда в UI

Их формулировка прямая: ограничения в бэкенде, не в интерфейсе, чтобы ни один вызывающий не мог заклинить клавиатуру. У них это подкреплено архитектурно: в wasm/WebHID-сборке те же тайминги продублированы в Rust-слое, а не оставлены на JS.

Для нас: соответствует FR3 (rate limiter внутри `psafety`) и риску №2 из architecture review («обход write-пути»). Добавляет аргумент к тому, что WebHID-сборка (SAFE_DEFAULT «после фазы 2») не может переиспользовать только протокольные кодеки — она обязана тянуть и слой ограничений, иначе браузерная сборка станет способом обойти защиту.

### 4. Stall — залипающее состояние, а не ошибка одной операции

Их модель: при stall'е выставляется флаг; повторное открытие устройства **не** восстанавливает его, а дополнительная активность держит его в этом состоянии; поэтому прекращается вообще всё, включая фоновое сканирование, до физического переподключения. Пользователю показывается ровно одно сообщение: выдерни, подожди десять секунд, вставь обратно.

Для нас: FR3 требует kill-switch без ретрая. Это уточняет: недостаточно не повторять команду — нужно **остановить и опрос тоже**, иначе поллинг UI сам поддерживает залипание. Прямое следствие для FR11: состояние устройства должно доезжать до UI событиями, а не опросом из UI, иначе мы получим тот же класс проблем.

Наблюдение о хрупкости их реализации: stall распознаётся сопоставлением подстрок в тексте ошибки `hidapi` (`Protocol error`, `ioctl`). Это работает, но зависит от формулировок чужой библиотеки. Нам стоит завести собственный тип ошибки транспорта с явным вариантом «endpoint stalled» и решать по коду ошибки платформы, а не по тексту — с фолбэком на текст, если платформа не даёт кода.

### 5. Кэш «живости» вместо опроса устройства

У них успешный обмен «ручается» за подключение на 20 секунд: пока кэш свеж, повторное сканирование отвечает из кэша и не выкладывает лишний identify-роунд-трип на провод. Причина названа прямо: фронтенд опрашивает, и каждый опрос конкурировал с реальной работой и добавлял к давлению записи, которое и приводит к stall'у.

Для нас: конкретный аргумент в пользу того, что `pcore` обязан держать модель состояния устройства и отдавать её UI, а UI не имеет права инициировать обращение к устройству ради обновления индикатора. Это уточнение к FR11 (Events для редких уведомлений) и к дизайну экрана Devices.

### 6. Один экземпляр приложения на устройство

У них подключён плагин single-instance с прямым обоснованием: две копии, разговаривающие с одной клавиатурой, дают достаточно устойчивого трафика, чтобы заклинить endpoint; повторный запуск поднимает уже открытое окно.

Для нас это **пробел в спецификации**, а не подтверждение. `spec.md` требует детектировать конфликт с *вендорским* софтом за config-endpoint, но ничего не говорит про вторую копию нашего собственного приложения — а это тот же конфликт, только его проще предотвратить. Внесено в `spec.md` (см. «Изменения в артефактах» ниже).

### 7. Журнал провода: только опкод и направление, без полезной нагрузки

У них кольцевой буфер на 48 последних обменов, в котором хранятся только время, направление и опкод. Обоснование: полезная нагрузка может содержать раскладку, а этот журнал попадает в лог, который пользователь вставляет в issue.

Для нас: у нас есть требование приватности (FR8) и журнал записей (FR3), но сформулированы они про Learning Mode capture и про факт записи. Здесь добавляется третий случай: **диагностический журнал, который пользователь куда-то отправляет**. Раскладка — это персональные данные (в ней бывают пароли в макросах), и она не должна попадать в такой журнал даже как «сырые байты для отладки». Внесено в `spec.md`.

### 8. Возможность подтверждается на уровне линии прошивки, а не семейства

Самое тонкое из их решений. Разрешение рисовать на экране выдаётся не по семейству, а по линии (по префиксу внутреннего имени платы), потому что в одном семействе рядом живут платы с разным разбором кадров. В их коде это зафиксировано тестом с прямой формулировкой: общее семейство — не доказательство. Платы линий, чья прошивка не разбиралась, остаются запрещёнными, хотя формально принадлежат «известному» семейству.

Более того, у них есть три разных уровня строгости в одном месте: семейство даёт право писать вообще (`writes_supported`), линия даёт право на конкретную возможность, а отдельные платы дополнительно отсекаются по числовым ограничениям (панель шире 255 px отклоняется, потому что прошивка читает габарит одним байтом и картинка ляжет косо, а не откажется).

Для нас: у нас двухуровневая модель — `protocol_family` + `confidence`. Этого недостаточно, и это не гипотеза, а наблюдение на 949 платах: **между семейством и платой есть уровень линии прошивки, и права выдаются на нём**. Наша схема реестра (`Приложение B`) это частично выдержит через `quirk`, но `quirk` семантически — «отклонение», а здесь речь о «на каком уровне доказана возможность». Отнесено в архитектурный чекпоинт перед фазой 3 (см. ниже), а не правится сейчас: изменение схемы реестра до появления первого engine — ровно та преждевременная фиксация, от которой предостерегает наше же architecture review.

### 9. Часть возможностей может быть известна только из реестра

У них есть флаг «есть боковая подсветка», и в комментарии сказано: прошивка отвечает на соответствующий GET-опкод независимо от того, есть ли физически подсветка, поэтому флаг реестра — единственный надёжный сигнал.

Для нас: это ещё один класс `origin`, которого в нашей шкале нет. Наши варианты (`Verified(hw)` / `FromFirmware` / `FromVendorJs` / `Assumed` / `Unsupported`) описывают, откуда мы узнали про **команду**. А «у этой модели физически нет такого светодиода» — факт о железе, полученный осмотром продукта, и он сильнее ответа прошивки. Отнесено в тот же архитектурный чекпоинт: возможно, нужен `origin: FromProductFact` или отдельная ось «свойство железа vs свойство протокола».

### 10. Тесты как защита инвариантов между дублирующимися артефактами

Их тестовый набор в модуле реестра — не про логику, а про согласованность артефактов. Примеры:
- каждый VID из реестра присутствует во всех трёх копиях udev-правила (в пакете, в UI-подсказке, в release notes) — с обоснованием, что правило уже разъезжалось дважды, и плата с пропущенным VID выглядит для пользователя как «правило не сработало»;
- любое устройство из реестра обязано попадать под сканирование по VID — иначе плата числится поддержанной, но никогда не будет найдена;
- флаг возможности не расходится с наличием соответствующей раскладки;
- у каждой платы непустая подпись для UI;
- права на запись выданы ровно тем семействам, что перечислены как известные;
- ручные правки реестра выживают его перегенерацию.

Плюс проверка в CI: генератор документа поддержки прогоняется, и сборка падает, если сгенерированный файл отличается от закоммиченного.

Для нас: это готовый шаблон CI-проверок для TICKET-07/14/18, и он бьёт в наш реальный риск. У нас будет ровно та же беда с дублированием (udev-правила на Linux — `spec.md` SAFE_DEFAULT «и пакет, и показ команды в UI», то есть минимум две копии) и с генерируемыми артефактами (SQLite из YAML). Заводить эти тесты дешевле сразу, чем после первого расхождения.

### 11. Ручные правки данных живут отдельным файлом и защищены тестом

Их генератор реестра извлекает каталог из вендорского бандла, но каталог со временем не является надмножеством себя: платы из него удаляются, а некоторые никогда не появлялись. Поэтому ручные добавления и правки лежат отдельным файлом и вливаются генератором, причём поддерживаются два вида записей: целая запись о плате и запись-переопределение отдельных полей. Тест падает, если перегенерация потеряла ручную правку; устаревшая правка (id появился в бандле) игнорируется и о ней сообщается, чтобы её удалили.

Для нас: это прямой ответ на главный риск TICKET-18 (ingestion pipeline) — «перегенерация тихо затирает ручные исправления». Модель «источник + файл переопределений + тест на выживание» переносится к нам без изменений по смыслу, при том что реализация будет своя (у нас YAML→SQLite, у них JS-бандл→JSON).

### 12. Идентификатор сборки с пометкой «грязного» дерева

Их build-скрипт вкладывает в бинарь короткий хеш коммита с суффиксом-маркером, если рабочее дерево изменено, и не вкладывает ничего, если это не git-чекаут. Отдельно проверяется, что берётся `.git` именно этого проекта: распакованный внутрь чужого чекаута тарбол иначе отрапортует чужой коммит, что в баг-репорте хуже, чем отсутствие коммита.

Для нас: пригодится для «отправить профиль устройства» (`spec.md`, вместо телеметрии) и для журнала. Мелочь, но без неё отчёт от сборки между релизами невозможно привязать. Заложить в TICKET-07 сразу, поскольку build-скрипт всё равно создаётся.

## Что мы делаем иначе — и почему это осознанно

Не всё их решение подходит. Различия зафиксированы, чтобы позже не «улучшить» наш план в их сторону, забыв причину.

1. **Реестр вкомпилирован как JSON и парсится целиком при каждом обращении.** У них функция «все устройства» десериализует 630 КБ JSON заново на каждом вызове, а поиск по идентификатору — линейный по этому результату. При их размере это работает, но у нас с первого дня заложен многосигнальный fingerprint (хеш report descriptor'а, набор TLC, строки, identify-опкод), то есть индексируемый поиск по нескольким ключам, а не один линейный проход по идентификатору. Наше решение YAML→SQLite остаётся в силе; их подход — свидетельство, что «просто данные в бинаре» жизнеспособны, а не аргумент против БД.

2. **Одна структура `DeviceSpec` описывает и идентификацию, и возможности, и раскладки, и экран.** Нам это не подходит: у нас есть слой capability с явным `origin` на каждую возможность — то есть возможности не могут быть плоскими полями структуры устройства. Их модель проще ровно потому, что у них нет ни Learning Mode, ни доказательной модели.

3. **Транспорт владеет handle напрямую, а конкурентность решается мьютексом вокруг всего состояния.** У них `Transport` держит устройство и мьютекс на «последнюю запись», а поверх — один общий мьютекс на всё состояние приложения. Это ровно тот failure mode «мьютекс вокруг одного handle», который наше architecture review (§6, REQUIRED_BEFORE_IMPLEMENTATION) запрещает и заменяет на `DeviceSession` с выделенным worker-потоком. Важно: у них это работает, потому что весь I/O — короткие синхронные обмены с блокирующими паузами внутри критической секции. Как только появится непрерывный аналоговый стрим (наш `he.analog_stream`, до 84 клавиш × 100–1000 Гц), эта схема перестанет работать: длинный читающий поток будет держать мьютекс. Наше решение остаётся, и теперь у него есть конкретное обоснование от чужого кода, а не только теоретическое.

4. **Ретраи внутри роунд-трипа.** Их обмен ждёт ответа с нужным опкодом до пяти попыток с растущей паузой. Для чтения это разумно. Для записи у нас правило жёстче: ошибка протокола при записи — немедленное закрытие сессии без ретрая (FR3). Разницу зафиксировать, чтобы «сделать как у них» не просочилось в write-путь.

5. **WebHID-сборка включает протокольные файлы по пути, а не через общий крейт.** У них браузерный крейт подключает файлы desktop-крейта напрямую по относительному пути, и в комментарии это обосновано (чтобы отправлять неизменённые сборщики пакетов). У нас есть нормальный workspace с крейтами, и такой приём означал бы отказ от границ, ради которых крейты и заводились. Наш путь: `pproto`/`pcaps` — обычные крейты-зависимости и для desktop-, и для будущей web-сборки.

## Ключевое наблюдение о масштабе (для архитектурного чекпоинта)

sharkfin покрывает keymap, RGB, макросы, профили, экраны, реестр на 949 плат, два семейства протокола и браузерную сборку — **одним крейтом на ~3400 строк Rust** с семью модулями. Наш план предусматривает девять крейтов до появления первого работающего engine.

Это не повод сворачивать план: у нас в scope есть то, чего у них нет вообще (доказательная модель `origin`, Learning Mode из четырёх уровней, генерация `SafeCommandId` на этапе сборки, аналоговый стрим, кросс-брендовые профили, мыши). Но это сильное свидетельство, что **девять крейтов до первого вертикального срезa — преждевременная структура**, и оно совпадает с тем, что наше собственное architecture review уже сказало в п.2: «риск в обратном — переусложнить границы крейтов до того, как появится хоть один protocol engine, который их проверит; тикеты фазы 1 должны поднять минимальный набор крейтов для одного read-only вертикального срезa, а не все девять».

Практический вывод для TICKET-07: поднять workspace со **всеми** крейтами по DAG (как требует тикет — это дешёвая фиксация направления зависимостей), но не наполнять их типами заранее. Реальные типы появляются в TICKET-10/11/12. Вопрос «не слить ли часть крейтов» ставится на архитектурном чекпоинте между фазами 3 и 4, когда будет первый работающий engine и станет видно, какие границы окупились. Заранее ни объединять, ни дробить — оба решения были бы без данных.

## Изменения в артефактах проекта, вытекающие из этого изучения

Внесено сейчас (additive, ни одно acceptance criterion не ослаблено):

1. **`spec.md` § Failure and fallback behavior** — требование единственного экземпляра приложения (метод 6).

3. **`spec.md` § Test seams** — диагностический журнал провода без полезной нагрузки (метод 7) и CI-проверки согласованности дублирующихся артефактов (метод 10).

Отнесено в архитектурный чекпоинт перед фазой 3 (не правится сейчас, потому что затрагивает схему реестра и модель `origin` до появления первого engine):

4. Уровень «линия прошивки» между семейством и платой, на котором выдаются права на возможность (метод 8).
5. Класс `origin` для факта о железе, известного только из реестра/осмотра продукта (метод 9).

7. TICKET-18 — модель «источник + файл переопределений + тест на выживание перегенерации» (метод 11).
