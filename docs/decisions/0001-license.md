# ADR-0001: Project license and third-party license policy

Дата: 2026-08-17 · Статус: accepted

## Контекст

Слой «keymap + RGB + макросы» на массовой платформе ROYUAN уже закрыт открытым проектом **sharkfin** (GPL-3.0, 943 модели). Он же — крупнейший доступный источник протокольных фактов. Другие полезные референсы (`libhmk`, `minipad-firmware`, `he-analog-gamepad`) — разные open-source лицензии; `libratbag` — MIT; `OpenRGB`/`OpenRazer` — GPL-2.0.

Продукт задуман как **коммерческое закрытое приложение** (владелец планирует продавать лицензии/копии), а не open-source проект по умолчанию.

GPL-3.0 не запрещает коммерциализацию как таковую (можно продавать копии), но требует, чтобы **любая распространяемая производная работа** тоже была GPL — то есть весь бинарь пришлось бы открывать. Это несовместимо с планом продавать закрытое приложение.

## Варианты

### A. GPL-3.0 для всего проекта
- Плюсы: прямое переиспользование кода sharkfin (экономия на ROYUAN-семействе), совместимость с экосистемой (OpenRGB/OpenRazer).
- Минусы: весь бинарь и любые форки обязаны остаться открытыми и GPL — несовместимо с закрытой коммерческой моделью.
- **Отклонён** — противоречит явному требованию владельца продукта.

### B. Proprietary / closed-source app, GPL-проекты только как prior art
- Плюсы: полная свобода коммерциализации, закрытый бинарь, никаких copyleft-обязательств.
- Минусы: нельзя ни строчки скопировать из sharkfin/OpenRGB/OpenRazer — весь protocol-engine код пишется с нуля по фактам (opcode'ы, смещения полей, report ID), а не по их исходникам. Дороже по времени, чем вариант A, но юридически безопаснее и соответствует бизнес-цели.
- **Выбран.**

### C. MIT/Apache-2.0 open-core
- Не рассматривался всерьёз в этой сессии — владелец продукта прямо сформулировал цель как «продавать закрытое приложение», не «open-core с закрытыми надстройками». Остаётся как возможный будущий пивот (см. «Последствия»).

## Решение

1. **Код приложения — proprietary.** Всё под `crates/` и `app/` — закрытый исходный код, принадлежит владельцу продукта. `LICENSE` в корне репозитория — proprietary-уведомление (не open-source лицензия).
2. **Зависимости (Cargo/npm) — только permissive.** Разрешены: MIT, Apache-2.0, BSD-2/3-Clause, ISC, Unlicense, CC0 (для данных). **Запрещены в шипящемся бинаре:** GPL-2.0, GPL-3.0, AGPL-3.0, LGPL (даже динамическая линковка LGPL требует юридической проверки — по умолчанию тоже запрещена без отдельного решения). Каждая новая зависимость проверяется на лицензию перед добавлением (`cargo-deny`/`cargo-license` в CI — см. тикет по workspace-скелету).
3. **Знания из GPL-проектов используются только в режиме «facts», как и описано в исходном плане (§7.3):**
   - *facts* (opcode, длина пакета, смещение поля, VID/PID) — можно использовать свободно, это факты о протоколе устройства, а не охраняемое авторским правом выражение;
   - *code* — из sharkfin/OpenRGB/OpenRazer (GPL) **никогда не копируется и не адаптируется построчно**; из libratbag (MIT) можно брать код при условии сохранения лицензионного уведомления и что итоговый файл/модуль остаётся совместим с proprietary-выпуском (MIT это позволяет);
   - *docs* — чужой текст не копируется, только конспект своими словами со ссылкой на источник.
4. **Реверс-инжиниринг бинарей/прошивок вендоров** — только для целей совместимости, только в изолированной VM, результат фиксируется как факты о протоколе (см. §7.3, §14 исходного плана), не как код.
5. **Данные устройств (`data/devices/*.yaml`, реестр, community-профили `.heprofile`) — открытый вопрос, не блокирующий.** Вероятный дефолт: лицензировать сам девайс-реестр отдельно от кода приложения (например, CC0-1.0 или собственная открытая data-лицензия), чтобы сообщество могло свободно присылать и переиспользовать `.heprofile`/device definitions даже если сам байт-код закрыт — это типичный паттерн (приложение закрытое, база данных открыта) и не противоречит цели монетизации приложения. Финальное решение — до Phase 4 (когда появится первый внешний community submission), см. `spec.md` § Open questions, помечено `SAFE_DEFAULT`.

## Последствия

- Больше первоначальной работы на протокол-инженерах: ROYUAN-протокол придётся выводить из **фактов** (probe/capture/diff по методологии Learning Mode, §8 исходного плана), а не портировать из sharkfin. Это удлиняет Phase 1/4 по сравнению со сценарием прямого заимствования кода, но устраняет юридический риск для коммерческого продукта.
- CI должен получить лицензионный линтер зависимостей (`cargo-deny` с deny-list GPL/AGPL/LGPL) с первого коммита workspace — иначе GPL-зависимость может проникнуть незаметно через транзитивный crate.
- `tools/ingest` (краулер/анализ вендорских бинарей) должен физически не попадать в релизный бинарь и не публиковаться — уже было верно в исходном плане (§3.2), теперь это ещё и лицензионное требование, не только репутационное.
- Если в будущем стратегия изменится (например, решение открыть часть кода) — это отдельный ADR, не тихая правка этого решения.
- Кооперация с автором sharkfin (см. `spec.md` — Decisions) ограничена обменом протокольными фактами/находками по железу, не совместным кодом и не общей лицензией.
