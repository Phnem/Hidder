# TICKET-06: Удалённая идентификация EPOMAKER (remote external validation)

## Status

DEFERRED_REMOTE_VALIDATION

**Reason (2026-08-17, вторая мутация дня):** устройство физически находится **не у разработчика**, а у другого человека (отец пользователя). Идентификация developer-инструментами на чужом ПК невозможна и не нужна: она потребовала бы установки Rust/cargo/Build Tools/USBPcap на чужую машину, что противоречит цели продукта и не даёт product-level валидации. Тикет **не отменён и не удалён** — он переносится из hardware-фазы (Phase 2) в **remote external validation track** и выполняется позже, по артефакту, который сгенерирует обычная пользовательская сборка Peripheral.

**Гейт входа — capability-based, а не «после фазы N»** (см. `MASTER_PLAN.md`, раздел о возврате EPOMAKER): существует обычная Windows-сборка, которая умеет (1) безопасно перечислить неизвестное устройство, (2) ничего в него не писать, (3) сгенерировать стандартный inventory/profile-артефакт, (4) автоматически редактировать серийник и прочие идентификаторы, не нужные для fingerprinting, (5) показать пользователю одну понятную кнопку **Export**. Естественная точка — после TICKET-13/14 либо как безопасный Level 0 внутри TICKET-16; форсировать сразу после TICKET-13 не следует, если UX всё ещё выглядит как инженерный debug tool.

## Supersedes

Этим тикетом заменён прежний TICKET-06 «Купить ROYUAN HE-клавиатуру» (мутация от 2026-08-17, полный прежний текст — в истории git, файл `06-purchase-royuan-board.md` до переименования). Прежняя редакция этого файла («Идентификация референсной платы EPOMAKER» как локальная работа фазы 2) заменена настоящей — см. Status.

- **Почему прежняя редакция больше не работает:** она исходила из того, что устройство лежит на столе разработчика. Это оказалось не так.
- **Чем заменена:** идентификация по артефакту, полученному удалённо от владельца устройства через обычную сборку приложения.
- **Ослаблены ли требования:** нет. Набор фактов, которые тикет обязан установить, **расширен** (см. Acceptance criteria), а условия получения данных стали строже — данные должны добываться приложением, а не человеком с отладочными инструментами.

## Objective

Установить по наблюдаемым данным и публичным источникам, что физически представляет собой EPOMAKER, находящаяся у стороннего владельца: маркетинговая модель, строки производителя/продукта, VID:PID, `bcdDevice`/release, тип клавиатуры, тип подключения, официальный конфигуратор, заявленные возможности и признаки OEM/контроллера/платформы — **каждый вывод с явной маркировкой confidence и evidence**.

**Ничего не принимать на веру по названию бренда.** EPOMAKER — брендодержатель, а не производитель контроллера; вывод о семействе делается многосигнально, по данным, а не по логотипу и не по VID:PID (`spec.md` § Domain rules).

Заранее **не назначать** EPOMAKER: вторым protocol family, HE-клавиатурой, ROYUAN, конкретным OEM, беспроводным устройством. Всё это устанавливается только по данным.

## User or system value

Тикет перестал быть подготовкой к лабораторному инвентарю и стал **первым реальным испытанием продуктового сценария**: способно ли приложение, разработанное на AULA, встретить неизвестное устройство на чужом ПК и самостоятельно собрать всё необходимое для его дальнейшего анализа — руками обычного пользователя, без dev-toolchain.

Это одновременно репетиция будущего community-submission workflow (TICKET-18) и проверка того, что в приложении не осталось AULA-специфичных предположений.

## Scope

Идентификация ведётся по двум источникам, и они не смешиваются:

1. **Артефакт от устройства** — inventory/profile-файл, полученный из TICKET-09 (remote inventory). Это evidence класса «наблюдение».
2. **Публичные источники** — страница вендора, документация конфигуратора, спецификации, обзоры. Это evidence класса «заявление вендора», оно ниже по весу и никогда не повышает confidence наблюдения.

Устанавливаемые пункты:

- точное маркетинговое имя модели, если его вообще можно установить;
- `manufacturer` / `product` strings (как они есть в устройстве, а не как на коробке);
- VID:PID;
- `bcdDevice` / release;
- тип клавиатуры (HE / механика / иное) — **только если подтверждаем**;
- тип подключения (USB / 2.4 ГГц / Bluetooth) — **только если подтверждаем**;
- официальный конфигуратор: существует ли, на чём сделан (WebHID / Electron / нативный / отсутствует), какой канал использует;
- заявленные вендором возможности: actuation, Rapid Trigger, DKS, SOCD, калибровка, макросы, RGB, профили;
- признаки OEM / контроллера / платформы: совпадения VID, узнаваемые строки, узнаваемая форма vendor-TLC, совпадения с каталогом TICKET-05.

## Out of scope

- Установка на компьютер владельца чего бы то ни было, кроме обычной сборки Peripheral. Ни Rust, ни cargo, ни Build Tools, ни Python, ни PowerShell-скриптов, ни USBPcap/Wireshark, ни ручного вызова HID API.
- Снятие самого инвентаря — это TICKET-09.
- Любая запись в устройство. Ни при каких обстоятельствах.
- Присвоение protocol family как факта. Максимум — кандидат с явной confidence.

## Acceptance criteria

- [ ] `docs/prior-art/epomaker.md` содержит карточку устройства по форме ниже.
- [ ] Указано точное маркетинговое имя модели, либо явно записано, что установить его не удалось, и почему.
- [ ] `manufacturer` / `product` strings зафиксированы по данным устройства.
- [ ] VID:PID зафиксирован по данным устройства, а не по продуктовой странице.
- [ ] `bcdDevice` / release зафиксирован.
- [ ] Тип клавиатуры записан **только если подтверждён**; иначе — «не подтверждено», с указанием, какими данными это можно было бы подтвердить.
- [ ] Тип подключения (USB / 2.4 / BT) записан **только если подтверждён**; иначе — «не подтверждено».
- [ ] Официальный конфигуратор найден и описан, либо явно записано «не найден».
- [ ] Заявленные возможности перечислены с пометкой источника (вендорская страница ≠ наблюдение).
- [ ] Признаки OEM / controller / platform названы вместе с основанием и confidence, либо явно записано «кандидата нет».
- [ ] **Каждый вывод несёт явную пару confidence + evidence.** Ни один пункт не помечен `Verified` без наблюдения на самом устройстве.
- [ ] Ни один вывод не сделан из бренда EPOMAKER.

Форма карточки:

```text
EPOMAKER <model | не установлено>

Marketing name:      ...                 (источник, confidence)
Manufacturer string: ...                 (из устройства)
Product string:      ...                 (из устройства)
VID:PID:             ...                 (из устройства)
bcdDevice/release:   ...                 (из устройства)
Keyboard type:       HE / mech / не подтверждено   (основание, confidence)
Layout:              ...
Connection:          USB / 2.4GHz / BT / не подтверждено
Configurator:        WebHID / Electron / native / none / unknown
Claimed features:    ...                 (источник: вендор)
OEM/controller/platform candidate: ...   (основание, confidence)
```

## Verification plan

Ручная: карточка существует; каждый пункт имеет источник и confidence; ни один пункт не выдан за проверенный факт без наблюдения; ни один вывод не опирается на бренд. Отдельно проверяется, что на компьютере владельца не устанавливалось ничего, кроме обычной сборки приложения.

## Expected architecture impact

- Пополняет карту TICKET-05 и даёт вторую fingerprint-запись для `pregistry`.
- **Q3 в `spec.md` остаётся открытым до выполнения этого тикета.** EPOMAKER заранее не считается беспроводной. Если позднее подтвердится доступный wireless/receiver config path и battery-телеметрия, это даёт реальное железо для `dev.connection` / `dev.power.battery` / `dev.power.charging` / Tray-UI раньше мышиной фазы. Если нет — исходная зависимость на будущую wireless-периферию остаётся. Capability-модель при этом не меняется: `dev.power.*` уже корректно обобщён на любое wireless-устройство.

## Risks

- **Соблазн классифицировать по бренду.** Прямо запрещён формулировкой тикета.
- **Соблазн компенсировать отсутствие устройства удалённой отладкой.** Прямо запрещён разделом Out of scope: если данных не хватает, чинится приложение, а не расширяется набор инструментов на чужом ПК.
- Владелец может иметь установленный вендорский софт, держащий config-endpoint. Приложение обязано это детектировать и сообщить (`spec.md`: конфликт детектируется, а не преодолевается силой), а не молча получить неполные данные.
- Модель может оказаться механической, а не HE. Это не провал: см. четыре исхода в `MASTER_PLAN.md` (Phase 5 / second protocol family).
