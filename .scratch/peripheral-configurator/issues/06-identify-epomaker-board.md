# TICKET-06: Идентификация референсной платы EPOMAKER

## Supersedes

Этим тикетом полностью заменён прежний TICKET-06 «Купить ROYUAN HE-клавиатуру» (запись мутации плана — ниже, полный прежний текст — в истории git, файл `06-purchase-royuan-board.md` до переименования).

- **Почему прежний тикет больше не нужен:** пользователь решил 2026-08-17, что ROYUAN-платы не будет. Покупка отменена.
- **Чем заменён:** вторым референсным устройством становится уже имеющаяся полноразмерная EPOMAKER.
- **Изменилась ли спецификация:** да — `spec.md` § Acceptance criteria (AC2/AC3) и раздел референсного железа переформулированы с «AULA + ROYUAN-плата (к покупке)» на «AULA + EPOMAKER (в наличии)». Ослабления критериев нет: требование ко второму устройству осталось тем же — полный read-only HID-инвентарь тем же транспортом.
- **Что изменилось по существу, а не по названию:** прежний тикет покупал устройство с *заранее предполагаемым* семейством (ROYUAN по VID). Новый тикет ничего не предполагает: принадлежность EPOMAKER к какому-либо семейству — то, что этот тикет обязан выяснить, а не то, из чего он исходит.

## Objective

Установить, что физически представляет собой имеющаяся полноразмерная EPOMAKER, по наблюдаемым данным и официальным материалам вендора: точная модель и аппаратная ревизия, Hall-Effect это или обычная механика, тип подключения (USB / 2.4 ГГц / Bluetooth), какой конфигуратор для неё существует и на чём он сделан, какие функции заявлены, и есть ли признаки принадлежности к известному OEM/protocol family.

**Ничего не принимать на веру по названию бренда.** EPOMAKER — брендодержатель, а не производитель контроллера; тот же бренд встречается и на ROYUAN-платформе, и на других. Вывод о семействе делается по данным, а не по логотипу.

## User or system value

Второе физическое устройство — единственный способ проверить, что `ptransport` действительно generic, а не написан под одну плату. Но чтобы инвентарь TICKET-09 был осмысленным, надо сначала знать, что именно в руках: модель, ревизия, тип подключения и наличие вендорского конфигуратора определяют, что вообще имеет смысл искать.

Отдельно: это первый случай в проекте, когда устройство классифицируется **до** того, как о нём что-то известно — то есть первая живая проверка принципа «сначала evidence, потом присвоение family».

## Dependencies

Нет. Устройство в наличии.

## Scope

- Точная модель и аппаратная ревизия (маркировка на корпусе/коробке/днище, ревизия PCB, если видна).
- Тип переключателей: Hall-Effect или обычная механика. Если HE — какие магнитные свитчи.
- Тип подключения: USB / 2.4 ГГц (ресивер) / Bluetooth, и какие из них доступны одновременно.
- VID:PID по факту подключения (Диспетчер устройств или enumeration), версия прошивки, если видна.
- Официальный конфигуратор: существует ли, на чём сделан (WebHID / Electron / нативный / отсутствует), какой канал использует.
- Заявленные вендором функции: actuation, Rapid Trigger, DKS, SOCD, калибровка, макросы, RGB, профили — что обещано.
- Признаки известного OEM: совпадения VID с известными платформами, узнаваемые строки, характерный конфигуратор, совпадения с каталогом из TICKET-05.

## Out of scope

- Enumeration TLC, чтение report descriptor'ов, любые обращения к vendor-коллекции — это TICKET-09.
- Любая запись в устройство. В этом тикете её нет ни при каких обстоятельствах.
- Присвоение protocol family как факта. Максимум — кандидат с явной confidence.

## Acceptance criteria

- [ ] `docs/prior-art/epomaker.md` содержит карточку устройства по форме ниже, с явной confidence на каждом неочевидном пункте.
- [ ] Тип клавиатуры (HE / механика) установлен и обоснован, а не предположен по названию модели.
- [ ] Тип подключения установлен для всех поддерживаемых каналов.
- [ ] VID:PID зафиксирован по факту подключения, а не по продуктовой странице.
- [ ] Кандидат в OEM/protocol family назван вместе с основанием и confidence, либо явно записано «кандидата нет».
- [ ] Ни один пункт не помечен как `Verified` — на этом этапе верификации железом ещё не было (она в TICKET-09).

Форма карточки:

```text
EPOMAKER <model>

Keyboard type:   HE / mechanical            (основание, confidence)
Layout:          full-size / ...
Connection:      USB / 2.4GHz / BT          (что доступно одновременно)
VID:PID:         ...                        (по факту подключения)
Firmware:        ...                        (если видна)
Configurator:    WebHID / Electron / native / none / unknown
Claimed features: ...
Known OEM candidate: ...                    (основание, confidence)
```

## Verification plan

Ручная: карточка существует, каждый пункт имеет основание, ни один не выдан за проверенный факт. Отдельно проверяется, что вывод об OEM не опирается на бренд.

## Expected architecture impact

Влияет на планирование TICKET-09 (что искать) и на TICKET-05 (карточка устройства пополняет карту). Один потенциально крупный эффект: если EPOMAKER окажется беспроводной, открытый вопрос **Q3** в `spec.md` меняет статус — он записан исходя из того, что ни одна референсная плата не беспроводная, и в этом случае tray/battery-трек (TICKET-20) перестаёт быть заблокированным до фазы 6.

## Risks

- **Соблазн классифицировать по бренду.** Прямо запрещено формулировкой тикета: EPOMAKER продаёт платы разных платформ.
- Вендорский конфигуратор может требовать установки ПО, которое само захватывает config-endpoint. Устанавливать его для изучения допустимо, но не одновременно с работой TICKET-09 (`spec.md`: конфликт за endpoint детектируется, а не преодолевается силой).
- Модель может оказаться механической, а не HE. Это не провал тикета: см. исход C в записи о фазе 2 (`MASTER_PLAN.md`) — устройство остаётся полезным как generic HID/transport test device.
