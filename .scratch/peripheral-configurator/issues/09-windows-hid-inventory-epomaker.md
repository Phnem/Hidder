# TICKET-09: Remote EPOMAKER inventory validation

## Status

DEFERRED_REMOTE_VALIDATION

**Reason (2026-08-17, вторая мутация дня):** EPOMAKER физически находится у стороннего владельца, не у разработчика. Developer-side HID-инвентарь (запуск `cargo run --example inventory` на машине с Rust-тулчейном) на чужом ПК невозможен и не нужен. Тикет **не отменён** — он переносится из Phase 2 в **remote external validation track** и полностью меняет способ получения данных: теперь их обязано добыть само приложение, а не человек с инструментами.

**Гейт входа — capability-based** (тот же, что у TICKET-06): существует обычная Windows-сборка Peripheral с безопасным read-only inventory и одной кнопкой **Export**. Естественная точка — после TICKET-13/14 или как безопасный Level 0 из TICKET-16, и не раньше, чем UX перестанет выглядеть как инженерный debug tool.

## Supersedes

1. Прежний TICKET-09 «HID-инвентарь ROYUAN-платы» — отменён вместе с покупкой платы (мутация 2026-08-17, текст в истории git).
2. Прежняя редакция «HID-инвентарь EPOMAKER на Windows + сравнение двух устройств» как developer-side работа фазы 2 — заменена настоящей.

**Что изменилось по существу:** предметом тикета перестал быть сам инвентарь (данные) и стал **сценарий их получения**. Раньше тикет проверял, что `ptransport` generic. Теперь он проверяет то же самое, но через продуктовый путь: приложение на чужом ПК, без единого инструмента разработчика.

**Ослаблены ли acceptance criteria:** нет. Прежний набор снимаемых полей сохранён целиком, сравнительный отчёт сохранён целиком, к ним добавлено более жёсткое условие на способ получения данных.

## Objective

Доказать, что **Peripheral на чужом Windows-ПК без dev-toolchain самостоятельно получает безопасный read-only инвентарь неизвестной EPOMAKER и экспортирует его в стандартный артефакт**, структурно сопоставимый с инвентарём AULA из TICKET-08.

Сценарий целиком:

```text
владелец устройства
        ↓
скачивает обычную сборку Peripheral
        ↓
запускает без Rust / dev-toolchain
        ↓
подключает EPOMAKER
        ↓
Peripheral обнаруживает устройство
        ↓
Export Device Report / Export .heprofile
        ↓
файл передаётся разработчику
        ↓
разработчик + публичные источники → TICKET-06 (модель / OEM / тип / возможности)
```

На компьютере владельца **не должны требоваться**: Rust, cargo, Visual Studio Build Tools, PowerShell-скрипты, Python, USBPcap/Wireshark, ручной вызов HID API, любые специальные debug-инструменты. Максимум — `скачать → запустить → подключить → Export`.

## User or system value

Три эффекта, и первый важнее остальных.

1. **Продуктовая валидация на неизвестном железе у постороннего человека.** Это единственный способ узнать, не осталось ли в приложении AULA-специфичных предположений, и достаточно ли понятен путь «неизвестное устройство → артефакт» для обычного пользователя. Лабораторный инвентарь этого не проверяет в принципе.
2. **Проверка, что `ptransport` действительно generic.** После одного устройства это неизвестно; транспорт, написанный под одну плату, выясняется только на второй.
3. **Вторые реальные данные для fingerprinting.** Сравнение двух настоящих дескрипторов впервые показывает, какие сигналы вообще различают устройства — ровно тот вопрос, ради которого существует `pregistry` (`spec.md` FR4).

Дополнительно это репетиция community-submission workflow (TICKET-18) на живом человеке, а не на гипотезе.

## Dependencies

Capability-гейт из раздела Status (сборка с безопасным export). TICKET-08 — источник эталонного формата и данных AULA для сравнения. TICKET-06 использует результат этого тикета как основной evidence, то есть порядок теперь **09 → 06**, а не наоборот.

**Ничего не блокирует.** TICKET-10, TICKET-11, TICKET-12, TICKET-13, TICKET-14 от этого тикета не зависят.

## Scope

Приложение обязано собрать и экспортировать тот же набор данных, что снят с AULA в TICKET-08, тем же кодом и в том же формате (`peripheral.hid-inventory/N`):

- все HID-интерфейсы и top-level collections;
- usage page / usage для каждой;
- VID:PID, `bcdDevice`/release, manufacturer/product strings;
- факт наличия серийника — **без самого значения** (см. Privacy);
- report descriptor (сырой hex) и его хеш;
- report IDs, размеры report'ов, наличие feature / input / output;
- что открывается, что не открывается и с какой ошибкой;
- тип подключения, насколько он наблюдаем.

И отдельно — четыре вопроса, на которые тикет обязан ответить явно (включая ответы «нет» и «не удалось определить»):

```text
есть ли config vendor TLC?
есть ли analog vendor TLC?
это одна коллекция или разные?
понадобился ли Win32 escape hatch?
```

### Сравнительный отчёт (обязательный артефакт)

```text
                              AULA Hero 84 HE   vs   EPOMAKER
VID:PID
release (bcdDevice)
manufacturer / product
USB interface count
TLC count
usage page / usage
report IDs
input / output / feature sizes
vendor-defined TLC
descriptor fingerprints
доступность коллекций
тип подключения
прочие наблюдаемые сигналы
```

### Privacy

Серийный номер и прочие идентификаторы, не нужные для fingerprinting, редактируются **по умолчанию** и без участия пользователя: в артефакт попадает `serial present: true`, а не значение. Это общая политика продукта, не AULA-специфичная (`spec.md` § Domain rules).

## Out of scope

- **Любой protocol probing и любые write-команды.** Remote inventory — строго read-only enumeration: никаких `WriteFile`/`HidD_SetFeature`, никаких safe probes, никакого захвата пользовательского ввода.
- Установка на компьютер владельца чего-либо, кроме обычной сборки приложения.
- Интерпретация протокола (что означают байты) — Learning Mode, TICKET-12+.
- Присвоение EPOMAKER protocol family как факта — из сравнения следует гипотеза с confidence, не `Verified`.
- Полноценный Learning Mode ради этого тикета. Если для продуктового пути нужен маленький переиспользуемый компонент `Export Device Report`, он выделяется отдельным узким тикетом или как ранняя часть Inventory Level 0 — read-only, без safe probes, без write, без capture пользовательского ввода, с serial redaction по умолчанию и versioned artifact schema. Расширять его в полный TICKET-16 раньше времени нельзя.

## Acceptance criteria

- [ ] Владелец устройства получил инвентарь, **не устанавливая** Rust, cargo, Build Tools, Python, USBPcap/Wireshark и не запуская никаких скриптов. Путь уложился в `скачать → запустить → подключить → Export`.
- [ ] Полный TLC-инвентарь EPOMAKER зафиксирован в том же формате, что у AULA, и структурно с ним сопоставим.
- [ ] Инвентарь снят тем же production-путём (`ptransport` + общий inventory-код), **без отдельной ветки под EPOMAKER**. Если ветка потребовалась — это зафиксировано как находка о generic transport abstraction, с решением, что менять в абстракции/транспорте (см. Risks).
- [ ] Ни одной write-операции и ни одного probe за время сценария; это подтверждается журналом.
- [ ] Серийник отсутствует в артефакте; присутствует только факт его наличия.
- [ ] На все четыре вопроса (config TLC / analog TLC / одна коллекция или разные / нужен ли escape hatch) дан явный ответ.
- [ ] Сравнительный отчёт двух устройств существует и заполнен по всем строкам.
- [ ] Классификация EPOMAKER записана ровно настолько, насколько позволяют наблюдаемые данные, с явной confidence и без опоры на бренд.
- [ ] Если vendor config TLC отсутствует или недоступен — это записано как **результат**, а не как неудача, вместе с тем, что приложение обязано в этом случае сказать пользователю `Config interface unavailable`, а не пытаться писать наугад.

## Verification plan

Прогон реального сценария на чужом Windows-ПК: владелец скачивает сборку, запускает, подключает устройство, жмёт Export, передаёт файл. Проверяется артефакт (схема, полнота, отсутствие серийника), журнал (отсутствие записей и probe'ов) и сравнительная таблица. Отдельно фиксируется, был ли запущен вендорский софт EPOMAKER в момент снятия и версия прошивки, если наблюдаема.

## Expected architecture impact

Четыре возможных исхода, все полезные:

- **Всё сработало без изменений** — первое свидетельство, что абстракция generic и что продуктовый путь работает на незнакомом железе. Не доказательство: два устройства это два устройства.
- **Понадобилась доработка транспорта** — лучше узнать это здесь, чем в фазе 5. Чинится **абстракция/транспорт**, а не создаётся vendor-specific enumeration.
- **Понадобился Win32 escape hatch на одном устройстве и не понадобился на другом** — прямо влияет на форму `platform::windows` и фиксируется как решение, а не локальный хак.
- **Устройство не отдало config-интерфейс** — валидный негативный compatibility case.

Сравнительный отчёт — второй реальный вход для `pregistry` (TICKET-10) и первый вход, полученный не в лаборатории.

## Risks

- **Появление `if epomaker { ... }` в транспортном слое.** Это архитектурное правило, уже принятое проектом: EPOMAKER проходит через тот же production pipeline, что и AULA. Обход правила ради получения данных обесценивает весь тикет — данные будут, а ответа на вопрос «generic ли транспорт» не будет.
- **Соблазн компенсировать отсутствие устройства удалённой отладкой.** Запрещено разделом Out of scope.
- **Соблазн классифицировать по бренду.** Ни один вывод не делается из названия.
- UX может оказаться недостаточно понятным для обычного пользователя. Это тоже результат тикета, а не помеха ему: он показывает, что сборку рано отдавать людям.
- Вендорский софт EPOMAKER, если запущен, может держать config-endpoint — приложение обязано это детектировать и сообщить.
- Результат специфичен для конкретной прошивки — фиксировать версию вместе с данными.
