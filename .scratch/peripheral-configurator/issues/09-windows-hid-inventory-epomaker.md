# TICKET-09: HID-инвентарь EPOMAKER на Windows + сравнение двух устройств

## Status

PENDING (blocked by TICKET-06, TICKET-08)

## Supersedes

Заменяет прежний TICKET-09 «HID-инвентарь ROYUAN-платы» (полный прежний текст — в истории git, файл `09-windows-hid-inventory-royuan.md` до переименования). Причина: ROYUAN-платы не будет (решение пользователя 2026-08-17), вторым референсным устройством становится имеющаяся EPOMAKER.

Что изменилось по существу: прежний тикет проверял конкретную гипотезу «ведёт ли себя ROYUAN-плата как описано у sharkfin». Новый ничего не проверяет о конкретном семействе — он снимает те же данные и **сравнивает** их с AULA, а вывод о родстве или различии делается из сравнения. Acceptance criteria не ослаблены: добавлен сравнительный отчёт, которого в прежнем тикете не было как отдельного артефакта.

## Objective

Снять полный read-only HID-инвентарь EPOMAKER на Windows **тем же самым `ptransport`**, которым только что исследовалась AULA, и построить сравнительный отчёт двух устройств.

Ключевое требование к реализации: **не писать отдельный диагностический код «под EPOMAKER»**. Если для второго устройства понадобился отдельный путь, это находка о `ptransport`, которую надо зафиксировать и исправить в `ptransport`, а не обойти в тикете.

```text
             ptransport
        ┌─────────┴─────────┐
        ▼                   ▼
   AULA inventory      EPOMAKER inventory
```

## User or system value

Два эффекта, и второй важнее первого.

1. **Проверка, что `ptransport` действительно generic.** После одного устройства это неизвестно. Транспорт, написанный под одну плату, выясняется только на второй, и дешевле выяснить это сейчас, чем в фазе 5.
2. **Первые реальные данные для fingerprinting.** До этого момента многосигнальный матчинг — теория из спецификации. Сравнение двух настоящих дескрипторов впервые позволяет сказать, какие сигналы вообще различают устройства:

```text
одинаковые VID/PID, разный дескриптор?
разные VID/PID, почти одинаковый дескриптор?
или устройства не имеют ничего общего?
```

Это ровно тот вопрос, ради которого существует `pregistry` (`spec.md` FR4 и доменное правило о том, что family не выводится из VID:PID).

## Scope

Тот же набор данных, что в TICKET-08, тем же кодом и в том же формате:

- все HID-интерфейсы и top-level collections;
- usage page / usage для каждой;
- VID:PID, manufacturer/product strings;
- report descriptor (сырой hex) и его хеш;
- report IDs, размеры report'ов, наличие feature / input / output;
- что открывается через `hidapi`, что не открывается и с какой ошибкой;
- поведение под elevated-процессом, если без него что-то недоступно.

И отдельно — четыре вопроса, на которые тикет обязан ответить явно:

```text
есть ли config vendor TLC?
есть ли analog vendor TLC?
это одна коллекция или разные?
понадобился ли Win32 escape hatch?
```

**Сравнительный отчёт** (обязательный артефакт этого тикета) — таблица вида:

```text
                     AULA        EPOMAKER
VID                  ...         ...
PID                  ...         ...
TLC count            ...         ...
Vendor TLC           ...         ...
Usage page           ...         ...
Report size          ...         ...
Descriptor hash      ...         ...
Feature reports      ...         ...
Analog interface     ...         ...
Configurator         ...         ...
```

## Out of scope

- Интерпретация протокола (что означают байты) — Learning Mode, TICKET-12+.
- **Любая запись в устройство.** Read-only enumeration, никаких `WriteFile`/`HidD_SetFeature`.
- Присвоение EPOMAKER какого-либо protocol family как факта. Из сравнения следует гипотеза с confidence, не `Verified`.

## Acceptance criteria

- [ ] Полный TLC-инвентарь EPOMAKER зафиксирован в том же формате, что у AULA.
- [ ] Инвентарь снят тем же `ptransport::enumerate()`, без отдельной ветки кода под конкретное устройство; если ветка потребовалась — это зафиксировано как находка о `ptransport` с решением, что с ней делать.
- [ ] На все четыре вопроса (config TLC / analog TLC / одна коллекция или разные / нужен ли escape hatch) дан явный ответ, включая «нет» и «не удалось определить».
- [ ] Сравнительный отчёт двух устройств существует и заполнен по всем строкам.
- [ ] Классификация EPOMAKER записана ровно настолько, насколько её позволяют наблюдаемые данные, с явной confidence и без опоры на бренд.
- [ ] Если vendor config TLC отсутствует или недоступен — это записано как **результат**, а не как неудача, вместе с тем, что приложение обязано в этом случае сказать пользователю (`Config interface unavailable`), а не пытаться писать наугад.

## Expected architecture impact

Три возможных исхода, все полезные:

- **`ptransport` подошёл без изменений** — первое свидетельство, что абстракция generic. Не доказательство: два устройства это два устройства.
- **Понадобилась доработка** — лучше сейчас, до того как на транспорт начнут писать protocol engines (TICKET-12).
- **Понадобился Win32 escape hatch на одном устройстве и не понадобился на другом** — это прямо влияет на форму `platform::windows` и должно быть зафиксировано как решение, а не как локальный хак.

Сравнительный отчёт — первый реальный вход для `pregistry` (TICKET-10): он покажет, какие сигналы фактически различают устройства, а какие бесполезны.

## Risks

- **Соблазн классифицировать по бренду** (см. TICKET-06). Ни один вывод не делается из названия.
- Устройство может оказаться механическим, а не HE (исход C из плана фазы 2). Тогда оно остаётся ценным как generic HID/transport test device, и тикет закрывается с этим выводом, а не считается проваленным.
- Вендорский софт EPOMAKER, если он установлен и запущен, может держать config-endpoint. Перед снятием инвентаря убедиться, что он не запущен, и зафиксировать это условие вместе с результатом.
- Результат специфичен для конкретной прошивки — фиксировать версию вместе с данными.
