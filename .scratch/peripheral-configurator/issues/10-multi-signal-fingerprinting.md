# TICKET-10: Многосигнальный fingerprinting устройства (`pregistry`)

## Status

READY (TICKET-07/08/11 выполнены; идёт **после TICKET-22**, чтобы проектироваться на всех наблюдавшихся topology, а не на одной)

## Objective

Реализовать `pregistry` со схемой из `spec.md` Приложение B и многосигнальным matcher'ом (report-descriptor hash → TLC-набор → manufacturer/product strings → safe identify-опкод → fw-версия → VID:PID), с explicit confidence, семя данными — **реальные данные AULA Hero 84 HE из TICKET-08**: descriptor topology, TLC, VID/PID, strings, report IDs и размеры, release, vendor-коллекции. Впервые реестр строится не теоретически, а против настоящего устройства.

**Обновлено 2026-08-18:** перед этим тикетом встал TICKET-22 — read-only инвентарь беспроводной мыши VXE Dragonfly R1 SE+ с 2.4 ГГц ресивером. Причина: до него у реестра была ровно одна topology (проводная клавиатура, 3 интерфейса, 7 TLC), и модель, спроектированная против одного примера, получилась бы keyboard-specific незаметно для всех. С TICKET-22 на входе оказываются **keyboard + mouse + receiver** и минимум три реальные topology.

Вопросы, которые из-за этого обязаны быть решены здесь, а не в фазе 6:

- одно физическое устройство с разными VID:PID в разных режимах подключения — одна запись реестра или несколько?
- ресивер и мышь — два устройства или одно с составной идентичностью?
- какие сигналы устойчивы к смене режима подключения, а какие меняются вместе с ним, и как это отражается на весах?

Отдельно: `SafetyGate::identify_device` (TICKET-11) сейчас принимает семейство **без confidence**. Этот тикет обязан довезти туда confidence — сегодня правилу «write только при `Verified`» нечего разрешать (write-команд ноль), но к TICKET-15 без этого останется дыра.

**Обновлено 2026-08-17 (вторая мутация дня):** тикет **не ждёт EPOMAKER**. EPOMAKER находится у стороннего владельца и переведена в remote-validation трек (TICKET-09/06); её fingerprint-запись добавляется отдельным follow-up, когда придёт удалённый артефакт. Одного устройства достаточно, чтобы построить схему, matcher и веса сигналов; ограничение «веса эвристичны, проверены на одном устройстве» фиксируется явно (см. Risks), а не обходится ожиданием.

## User or system value

Прямая реализация ключевого доменного правила спецификации: "family нельзя вывести из PID". Без этого TICKET-12 (первый protocol engine) не может безопасно решить, можно ли доверять устройству чтение/запись.

## Dependencies

TICKET-08 (реальные TLC/дескрипторы AULA), TICKET-22 (topology мыши и ресивера во всех режимах), TICKET-07, TICKET-11 (гейт, куда доезжает confidence).

## Scope

- SQLite-схема, сгенерированная из YAML (`data/devices/aula-hero84-he.yaml` как первая запись, по шаблону §19.1 плана).
- Записи для VXE Dragonfly R1 SE+ по данным TICKET-22 — по одной на каждую наблюдавшуюся topology, либо одна составная: **что именно правильно, решает этот тикет**, и решение обосновывается данными, а не удобством схемы.
- `fingerprint` таблица с весами сигналов (report_descriptor_sha256 — самый сильный, VID:PID — самый слабый, индекс).
- Confidence enum: `unknown | candidate | high | verified` (как в шаблоне устройства §19.1).
- Правило: запись в устройство разрешена только при `confidence >= verified` для конкретной `protocol_family` — сам gate реализуется в `psafety` (TICKET-11), но `pregistry` обязан отдавать confidence наружу как часть контракта.

## Out of scope

- Запись EPOMAKER в реестр — данные придут из remote-валидации (TICKET-09). Тикет этим **не блокируется**: запись добавляется отдельным follow-up, когда артефакт получен.
- Мышиный протокольный слой, `MouseProtocol`, DPI/polling/кнопки — фаза 6 (TICKET-19). Из TICKET-22 сюда приходит только identity и topology, не протокол.
- UI для отображения confidence — TICKET-13.

## Acceptance criteria

- [ ] `pregistry` компилируется, YAML → SQLite build-шаг работает.
- [ ] Первая реальная запись устройства (AULA Hero 84 HE) с данными из TICKET-08 (report descriptor hash, TLC-набор) присутствует в `data/devices/`.
- [ ] Matcher возвращает confidence и объясняет, какие сигналы совпали (не просто true/false).
- [ ] Записи VXE Dragonfly R1 SE+ по данным TICKET-22 присутствуют, и в тикете зафиксировано, почему выбрана именно эта модель идентичности (одна запись на режим против одной составной).
- [ ] Matcher корректно ведёт себя на одном физическом устройстве в разных режимах подключения: результат не должен быть «два неизвестных устройства», если данные позволяют увидеть одно.
- [ ] Ресивер и устройство за ним различимы в модели, либо явно записано, что наблюдаемые данные их не различают.
- [ ] Confidence доезжает до `SafetyGate::identify_device` (`psafety`, TICKET-11).
- [ ] Unit-тесты: matcher корректно различает два устройства с одинаковым VID:PID, но разным report descriptor hash (регрессионный тест на "PID переиспользуется" из доменных правил).

## Verification plan

`cargo test -p pregistry`; ручная проверка, что реальный AULA report descriptor (из TICKET-08) матчится с `confidence: verified` после ручного ввода его как эталона.

## Expected architecture impact

Формирует финальный публичный контракт `pregistry` (не только схему, но и matcher API), на который будет опираться TICKET-12.

## Risks

- Веса сигналов (§6.2 плана) — эвристика. После TICKET-22 она проверяется на **двух физических устройствах разных категорий** и нескольких topology, что заметно лучше одной клавиатуры, но всё ещё далеко от рынка. Третье устройство (EPOMAKER) придёт удалённо и позже (TICKET-09). Явно зафиксировать как «первая итерация, пересмотреть после первого remote-артефакта и после Phase 4/5» в implementation notes при закрытии тикета.
