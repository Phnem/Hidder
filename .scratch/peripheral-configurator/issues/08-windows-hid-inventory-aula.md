# TICKET-08: Ключевой эксперимент — HID-инвентарь AULA Hero 84 HE на Windows

## Status

DONE_WITH_DEVIATIONS (2026-08-17) — инвентарь снят полностью, на все четыре вопроса дан ответ; один вопрос (analog TLC) закрыт ответом «не удалось определить без I/O», что тикетом прямо разрешено. См. Deviations.

## Objective

Реализовать `ptransport::enumerate()` через `hidapi` (Windows-backend — `hid.dll`/Win32 HID API) и вывести полный HID-инвентарь AULA Hero 84 HE на Windows: какие TLC реально открываются, какие дают `ERROR_ACCESS_DENIED`, доступен ли vendor-defined TLC (и, если да, содержит ли он аналоговый стрим). Если `hidapi` не даёт доступа к нужной информации об TLC/access-статусе — использовать прямой Win32 (`CreateFile`+`HidD_*`) как **локальный escape hatch внутри `ptransport`**, не как основной путь (см. `spec.md` FR7).

## User or system value

Это фундаментальный эксперимент, от которого зависит вся Windows-часть архитектуры (§5, §18 шаг 6 плана). Пока он не сделан, предположение "hidapi/Win32 открывает vendor-defined TLC как у sharkfin" — гипотеза, а не факт. Подтверждает или опровергает AC3 из `spec.md`.

## Dependencies

TICKET-07 (workspace/crate skeleton) — **выполнен**.

Замечание из ревью TICKET-07, адресованное этому тикету: `hidapi::HidError` уже протекает в `TransportError` как источник `#[from]`. Это тип ошибки, а не handle, доступа к устройству он не даёт — но при добавлении реального I/O проверить, что вместе с ним не начали протекать другие типы `hidapi`.

## Scope

- `ptransport::enumerate()` — перечисление всех HID top-level collections устройства через `hidapi`, без утечки `hidapi::HidDevice`/Win32-типов наружу крейта (см. architecture review §6/§9).
- Enumeration-путь не обязан ещё владеть устройством через полноценную `DeviceSession` (это read-only разведочный код), но должен возвращать данные через типы, совместимые с будущим `DeviceSession`-контрактом из TICKET-07/11 — не через голый `HidDevice`.
Снимается (уточнено 2026-08-17 — этот же список дословно повторяет TICKET-09 для второго устройства, чтобы отчёты были сравнимы построчно):

```text
все HID-интерфейсы
top-level collections
usage page / usage
VID / PID
manufacturer / product strings
report descriptor (сырой hex) + его хеш
report IDs
размеры report'ов
наличие feature / input / output report'ов
что открывается через hidapi
что не открывается и с какой ошибкой
```

И отдельно — четыре вопроса, на которые тикет обязан ответить явно, включая ответ «нет» и «не удалось определить»:

```text
есть ли config vendor TLC?
есть ли analog vendor TLC?
это одна коллекция или разные?
понадобился ли Win32 escape hatch?
```

- Для каждого TLC: попытка открытия + результат (успех / `ERROR_ACCESS_DENIED` / другая ошибка); при отказе — повторная проверка под elevated-процессом.
- Эвристика для vendor-defined канала: usage page `0xFF00`–`0xFFFF`. Это эвристика поиска, а не признак семейства — совпадение с параметрами ROYUAN (`0xFFFF`, usage 2) ничего не доказывает о принадлежности AULA, и обратное тоже.
- Результат — дамп в `EXECUTION_LOG.md` и человекочитаемый отчёт; сырые данные (hex дескриптора) сохраняются целиком, а не в пересказе: они станут входом для fingerprinting в TICKET-10.

**Никаких write-команд**, ни при каких условиях, включая «просто проверить, отвечает ли».

## Out of scope

- Интерпретация протокола (что означают байты) — это Learning Mode, TICKET-12+.
- Запись каких-либо данных в устройство — этот тикет **read-only enumeration only**, никаких `WriteFile`/`HidD_SetFeature`.

## Expected architecture impact

Определяет финальную форму `ptransport`'s public API (`DeviceId`/`SessionHandle`-совместимые типы, `TlcDescriptor` и т.п.) — первый реальный потребитель контракта, заложенного в TICKET-07. Также первая точка, где решается, нужен ли escape hatch на прямой Win32 в принципе, или `hidapi` достаточно для всех нужных данных (report descriptor, access-статус per-TLC) — фиксировать это решение в Implementation notes при закрытии тикета.

## Risks

- Аналоговый стрим может сидеть в той же коллекции, что и стандартный keyboard input report → недоступен через hidapi так же, как через WinRT (открытый вопрос Q2 в `spec.md`). Если так — зафиксировать честно, не предполагать успех.
- Результат специфичен для конкретной прошивки AULA Hero 84 HE — зафиксировать версию прошивки вместе с результатом.

## Implementation notes

### Что реализовано

`ptransport::inventory`: `Hid` (владеет `HidApi`, наружу ни один тип `hidapi` не выходит), `HidCollection`, `CollectionAccess`, `Hid::enumerate()` и `Hid::inspect()`. Плюс dev-инструмент `crates/ptransport/examples/inventory.rs`, который печатает обзор, снимает полный инвентарь одного устройства и пишет два артефакта (`.json` схемы `peripheral.hid-inventory/1` и `.md`). Формат описан в `docs/hardware/README.md`.

Кода «под AULA» нет: инструмент фильтрует по VID:PID, переданному аргументом, и ничего не знает ни про одно конкретное устройство. TICKET-09 запускает ту же команду с другим `--device`.

Попутно закрыто замечание из ревью TICKET-07: `hidapi::HidError` больше не протекает в публичный API — `TransportError::Hid(#[from] hidapi::HidError)` заменён на `TransportError::Backend(String)`.

### Что снято с железа

Устройство: **VID `0x372E`, PID `0x103E`**, manufacturer `BY Tech`, product `HERO 84 HE`, release `0x0216`, серийный номер присутствует (значение в артефакт не пишется — см. находку 5). Windows 11, без прав администратора.

**7 top-level collections на 3 USB-интерфейсах, все открылись:**

| if | usage page:usage | тип | report ID | размеры на проводе (вкл. байт ID) | дескриптор |
|---|---|---|---|---|---|
| 0 | `0x0001:0x0006` | boot keyboard | — (без ID) | in 8, out 1 | 66 B |
| 1 | `0x0001:0x0002` | mouse | 2 | in 5, feature 2 | 76 B |
| 1 | `0x0001:0x0006` | keyboard (NKRO, 120 бит) | 7 | in 16 | 65 B |
| 1 | `0x0001:0x0080` | system control | 5 | in 2 | 29 B |
| 1 | `0x000C:0x0001` | consumer control | 4 | in 3 | 25 B |
| 2 | **`0xFF00:0x0001`** | **vendor-defined** | 3 | **feature 64** (только feature) | 25 B |
| 2 | **`0xFF60:0x0061`** | **vendor-defined** | 9 | **in 64 / out 64** (без feature) | 36 B |

Полные дескрипторы (hex) и FNV-хеши — в `docs/hardware/aula-hero-84-he.{json,md}`.

### Ответы на четыре обязательных вопроса

1. **Есть ли config vendor TLC?** — **Да, и их два**, оба на интерфейсе 2: `0xFF00:0x0001` (только feature-репорты, 64 байта на проводе) и `0xFF60:0x0061` (input и output по 64 байта, feature нет). Какой из них является каналом конфигурации — **неизвестно и в этом тикете неустановимо**: чтобы различить, нужно что-то отправить.
2. **Есть ли analog vendor TLC?** — **Не удалось определить.** Дескриптор описывает форму, а не смысл: 63-байтный input-поток на `0xFF60:0x0061` по форме подходит под аналоговый стрим (у prior art аналоговые кадры приходят именно input-репортами на vendor-интерфейсе), но подтвердить это можно только чтением, которое тикет запрещает. Кандидат есть, факта нет.
3. **Одна коллекция или разные?** — **Разные**, и это самая интересная находка: два разных vendor-TLC с разной механикой обмена (feature против input/output) на одном USB-интерфейсе. Это не «канал и его дубль», это две разные двери.
4. **Нужен ли Win32 escape hatch?** — **Для этого тикета нет.** `hidapi` выдал всё: перечисление, строки, report-дескрипторы, открытие. Escape hatch не добавлялся. Единственный пробел, который `hidapi` не закрывает, зафиксирован как находка 2, и решение по нему отложено до первого реального I/O (TICKET-12), а не принято сейчас.

### Находки

**1. AULA — не ROYUAN, и теперь это факт, а не предположение.** VID `0x372E` отсутствует в списке ROYUAN-семейства из `docs/prior-art/royuan.md` (`0x3151`, `0x379a`, `0x374a`, `0x38a9`, `0x046a`, `0x2ea8`, `0x145f`). Форма vendor-канала тоже другая: у ROYUAN это usage page `0xFFFF`, usage `2`, report ID `0`; здесь — `0xFF00:0x0001` с report ID `3` и `0xFF60:0x0061` с report ID `9`. Совпадает только размер кадра (64 байта), а он у половины периферии такой.

**2. «Открылось» — более слабое утверждение, чем кажется, и `hidapi` не даёт его усилить.** На Windows backend при отказе в read/write открывает устройство с нулевыми правами доступа; дескрипторы и строки при этом читаются. То есть `opened = true` означает «доступ уровня перечисления получен», а не «с устройством можно разговаривать». Различить можно только отправив репорт — что запрещено. Записано в документации типа и в `docs/hardware/README.md`, чтобы TICKET-09 и TICKET-12 не прочитали это как «доступ есть».

**3. Классифицировать ошибки `hidapi` по тексту невозможно в принципе.** Backend отдаёт сообщение без кода ошибки, а на Windows это локализованный текст ОС — на этой машине он был бы русским. Prior art (sharkfin) определяет stall подстрокой `Protocol error`; на локализованной системе такой тест молча не сработает. Отсюда: `TransportError::Backend(String)` документирован как непрозрачный текст для лога, а `EndpointStalled`/`AccessDenied` должны определяться кодом платформы, а не текстом. Это уточняет требование к kill-switch (FR3) и является конкретным аргументом за escape hatch — но не сейчас, а когда появится реальный I/O.

**4. Устройство требует пересмотра модели `DeviceSession` (FR10).** Спецификация говорит «одно устройство — одна `DeviceSession`, владеющая физическим handle». Здесь одно физическое устройство = 7 открываемых коллекций с разными путями, и как минимум две из них (оба vendor-TLC) потенциально нужны одновременно: конфигурация через одну, аналоговый стрим через другую. Значит сессия владеет **набором** handle'ов, по одному на коллекцию, а не одним. Это не противоречит FR10 по сути (handle по-прежнему не покидает крейт и I/O по каждому идёт в своём worker'е), но формулировка «одна сессия — один handle» неточна. Отнесено в архитектурный чекпоинт перед фазой 3.

**5. Артефакт инвентаря содержал уникальный серийный номер устройства.** Обнаружено при первом прогоне. Серийник — идентификатор конкретного экземпляра; артефакты коммитятся, и той же формы артефакты станут community-submission'ами в TICKET-18, то есть серийник превратился бы в сквозной трекинг-идентификатор чужой клавиатуры. Исправлено: по умолчанию пишется только факт наличия (это сигнал для fingerprinting), значение — только по явному флагу `--include-serial`, который не предназначен для коммита. Это третий приватный контур наряду с capture-логом и журналом провода.

**6. `hidapi` видит не всё, что есть у устройства — проверено отдельно.** Перечисление HID не покажет non-HID интерфейс (WinUSB/CDC), если он есть. Сверено через `Get-PnpDevice`: у платы ровно три USB-интерфейса (`MI_00`, `MI_01`, `MI_02`), все HID, и они дают ровно 1 + 4 + 2 = 7 коллекций — совпадает с инвентарём. Скрытых интерфейсов нет. Приём записан в `docs/hardware/README.md` как обязательная проверка полноты для TICKET-09.

**7. `0xFF60:0x0061` — известная по соглашению пара.** Именно эти usage page и usage использует raw-HID интерфейс QMK/VIA. Это наблюдение о числах, **не вывод о прошивке**: значения общедоступны и переиспользуются массово, а размер кадра здесь 64 байта против 32 у типичного QMK. Заносится как кандидат-гипотеза с низкой уверенностью для TICKET-05/10, и ни в коем случае не как «плата на QMK».

### Влияние на открытые вопросы спецификации

- **Q2** (сидит ли аналоговый стрим в отдельном доступном vendor-TLC): для AULA получено **положительное свидетельство по доступности** — vendor-TLC существует, открывается без admin и имеет двусторонний 64-байтный канал. Сам факт наличия аналогового потока в нём **не подтверждён**. Q2 остаётся открытым.
- **AC3**: подтверждён для AULA на уровне enumeration, с оговоркой находки 2.

## Deviations

1. **Вопрос про analog TLC закрыт ответом «не удалось определить».**
   - **Planned:** «доступен ли vendor-defined TLC (и, если да, содержит ли он аналоговый стрим)».
   - **Actual:** доступность подтверждена; содержимое — нет.
   - **Reason:** определить содержимое канала можно только обменом с устройством, а тикет (и прямое указание пользователя) это запрещают. Тикет сам предусматривает ответ «не удалось определить» как валидный.
   - **Consequence:** Q2 не закрыт. Следующая возможность — TICKET-12 (первый engine, чтение под `psafety`), не раньше.
   - **Follow-up:** учтено в TICKET-12/15.

2. **Проверка под elevated-процессом не выполнялась.**
   - **Planned:** «если недоступен без admin — повторная проверка под elevated».
   - **Actual:** не выполнялась.
   - **Reason:** условие не наступило — все семь коллекций открылись обычным процессом.
   - **Consequence:** нет данных о поведении под elevated. Они и не нужны, пока ничего не отказывает.
   - **Follow-up:** нет.

3. **Добавлен dev-инструмент и артефакты, формально шире «дампа в EXECUTION_LOG».**
   - **Planned:** «результат — дамп в `EXECUTION_LOG.md` и человекочитаемый отчёт».
   - **Actual:** машиночитаемый JSON + сгенерированный markdown + `docs/hardware/README.md`, а в `EXECUTION_LOG.md` — сводка и находки.
   - **Reason:** требование фазы 2 о построчной сравнимости с TICKET-09 недостижимо, если результат — прозаический дамп в журнале.
   - **Consequence:** появился формат артефакта, который придётся поддерживать. Версионирован схемой с первого дня.
   - **Follow-up:** нет.

4. **Изменён публичный тип ошибки `ptransport`.** `TransportError::Hid(#[from] hidapi::HidError)` → `Backend(String)`. Это исполнение замечания из ревью TICKET-07, адресованного этому тикету; не расширение скоупа.

## Review findings

Самопроверка против acceptance criteria, ограничений тикета и рисков architecture review:

- **Read-only соблюдён.** В коде нет ни одного вызова записи: `write`, `send_feature_report`, `get_feature_report` и чтение input-репортов отсутствуют как класс. Проверено просмотром `inventory.rs` — используются только `device_list`, `open_path`, `get_report_descriptor`. **PASS**
- **Приватность.** Ни один input-репорт не читается, значит нажатия клавиш физически не могли попасть никуда. Серийный номер исключён из артефакта. **PASS**
- **Отсутствие AULA-specific путей.** Инструмент параметризован VID:PID; в `ptransport` нет ни одного упоминания конкретного устройства. **PASS**
- **Утечка типов из `ptransport` (риск №1 review).** `hidapi` полностью инкапсулирован: `Hid` владеет `HidApi`, публичные типы — собственные, `HidError` больше не в публичном API. **PASS**
- **Escape hatch не добавлен без необходимости.** Пробел `hidapi` зафиксирован как находка, решение отложено. **PASS**
- **Сравнимость с TICKET-09.** Один инструмент, одна схема, формат задокументирован. **PASS**
- **Скоуп.** Ни строки интерпретации протокола, ни одного опкода, ни одной записи в реестр. **PASS**

Замечание (не блокирующее): парсер report-дескрипторов живёт в примере, то есть вне продуктовых крейтов и вне fuzz-покрытия. Это осознанно — продуктовый парсер читает недоверенный вход и приезжает с `pregistry` в TICKET-10 вместе с фаззингом (`spec.md` § Test seams). Дублирования не возникнет: парсер примера умеет только считать размеры и должен быть удалён, когда появится продуктовый.

Блокирующих findings нет.
