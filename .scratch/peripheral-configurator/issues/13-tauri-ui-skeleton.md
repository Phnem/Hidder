# TICKET-13: Tauri UI skeleton — Devices + HE (read-only) + Journal

## Status

DONE_WITH_DEVIATIONS (2026-08-19, closed)

## Objective

Собрать минимальный Tauri+React UI с тремя экранами: Devices (карточка устройства, статус подключения), HE (read-only отображение actuation/RT значений из TICKET-12), Journal (список исполненных `SafeCommandId` из TICKET-11).

## User or system value

Первая точка, где результат Phase 1 виден не только разработчику в консоли, но и как реальный продукт — прямая демонстрация AC2 из `spec.md`.

## Dependencies

TICKET-07 (app skeleton существует), TICKET-12 (нужны реальные данные для отображения), TICKET-11 (Journal-данные).

## Scope

- Экран Devices: карточка AULA Hero 84 HE, статус "подключено"/"нет устройства"/"конфликт с вендорским софтом" (детекция конфликта — минимальная эвристика на этом этапе, не полная реализация).
- Экран HE: визуальный layout клавиатуры (можно упрощённый placeholder-layout на этом этапе, не полноценный KLE-импорт — это SAFE_DEFAULT из `spec.md`, реализуется позже), отображение actuation/RT значений per-key, помеченных `origin`.
- Экран Journal: таблица исполненных команд с таймстампом.
- IPC между UI и `pcore` (Rust) закладывается сразу тремя механизмами (`spec.md` FR11, architecture review §6): Tauri **commands** для запросов вида "получить состояние Devices/HE/Journal", Tauri **events** для низкочастотных уведомлений (`device_connected`/`device_disconnected`/`protocol_error`), и зарезервированный, но пока пустой канал **Channels** для будущего `he.analog_stream` — этот тикет не реализует Analog Monitor, но обязан не завести никакой высокочастотный поток через общий event bus, который потом придётся переделывать.
- Дизайн-принцип из spec.md соблюдён с первого экрана: неподтверждённые (`Assumed`) capability не показываются как рабочий контрол.

## Out of scope

- Редактирование значений (write) — Phase 2, не этот тикет (UI в этом тикете строго read-only, симметрично TICKET-12).
- Analog Monitor, Profiles, Learning Mode экраны — появляются в соответствующих будущих эпиках (issues 15/16).

## Acceptance criteria

- [x] Приложение запускается, показывает реальное состояние AULA Hero 84 HE при подключении (не мок-данные). Проверено на железе 2026-08-19: четыре реальных устройства, `aula-hero84-he [verified]`, model id 18691697672197, W 0.51 / A 1.02 / S 1.49 / D 2.00 мм.
- [x] HE-экран показывает только capability с `origin: Verified(hw)`; ничего не показывается как интерактивный контрол записи. Держится **типом**, а не разметкой: `pcaps::CapId` — закрытый enum с одним вариантом, контролу rapid trigger не к чему привязаться.
- [x] Journal-экран отображает реальные записи из `psafety` — две записи, `read_model_id` и `read_key_travel`, с временем и классом `safe_read`.
- [x] Отключение устройства корректно отражается в UI. **Частично:** разрыв сессии (Disconnect) проверен на железе — значения пропадают, статус меняется; физическое выдёргивание кабеля **не проверено** (см. Deviations 6).

## Verification plan

Ручное тестирование в браузере/Tauri-окне с реальным устройством: подключить → увидеть карточку и значения → отключить → увидеть смену статуса. Frontend unit-тесты на IPC-контракт (моканое `pcore`).

## TDD classification

RECOMMENDED (IPC-контракт и state-management — интеграционный шов, TDD где практично; чисто визуальная вёрстка — NOT_NEEDED, см. классификацию плана).

## Expected architecture impact

Формирует трёхканальный IPC контракт `pcore` ↔ UI (commands/events/channels), который будет расширяться, но не переосмысливаться радикально в последующих эпиках (write, Analog Monitor) — при условии, что Channels зарезервированы под высокочастотные потоки уже сейчас, а не введены постфактум в Phase 2.

## Risks

Нет существенных сверх обычных UI-рисков.

## Implementation notes

### Что сделано (2026-08-19)

Три экрана поверх реального `pcore`, без мок-данных нигде, плюс два слоя,
которых до этого тикета не было: сервис устройств в `pcore` и трёхканальный IPC,
заполненный целиком.

**`pcore::service` — поток, владеющий железом.** Приложению нужно было что-то
`Send + Sync`, и честных вариантов было два: мьютекс вокруг `Peripheral` или
выделенный поток. Мьютекс — это ровно та форма, которую запрещает FR10
(несколько вызывающих по очереди дёргают один handle с произвольного потока
рантайма UI, а HID-чтение блокирующее). Поэтому один поток, очередь заданий,
`DeviceService` как ручка. Это **не** полноценная `DeviceSession` из FR10 — та
владеет handle'ами всю свою жизнь и строится в TICKET-15 под аналоговый стрим;
это та же форма одним слоем выше, появившаяся раньше по необходимости.

**Watcher, и граница, которую он обязан соблюдать.** Экран, показывающий
клавиатуру, выдернутую десять минут назад, — это прямо тот провал, который
называет acceptance criteria, и UI не имеет права чинить его опросом. Поэтому
состояние приходит событиями снизу. Ключевое разделение — между двумя вещами,
которые звучат одинаково:

- **enumeration** спрашивает операционную систему, что подключено. Ничего не
  открывает и ничего не шлёт — это и крутится раз в 2 секунды;
- **identification** читает report-дескрипторы, то есть открывает handle на
  каждую коллекцию. Выполняется **один раз на устройство**, при появлении.

Watcher, не разделявший бы их, открывал бы каждую HID-коллекцию на машине
каждый тик. `Peripheral::present` / `Peripheral::identify` разведены ровно
поэтому, `discover` остался как их композиция.

**Найденная дыра в транспорте: перечисление отвечало из кэша.** `hidapi`
строит список устройств один раз, при открытии контекста; без
`refresh_devices()` устройство, выдернутое позже, продолжало бы числиться
подключённым **навсегда**, а подключённое позже — не появлялось бы никогда. То
есть acceptance criteria про отключение было недостижимо по причине уровнем
ниже UI. Добавлен `ptransport::Hid::refresh`.

**Журнал переехал из сессии к вызывающему.** Было: `connect()` создавал
`JournalLog` внутри и отдавал его внутри `DeviceSession`. Следствие — записи
**неудавшегося** подключения умирали вместе с сессией, которой не случилось,
то есть терялось ровно то, ради чего журнал существует. Теперь журнал
принадлежит вызывающему (`Peripheral::connect(&discovered, &mut journal)`), один
на процесс, и отказы с ошибками попадают в него наравне с успехами.

**Одни часы на процесс.** `SafetyGate` строится на операцию, а
`MonotonicClock::default()` обнуляется при создании — значит каждая запись
журнала получала время около нуля, и колонка времени была бы бессмысленной.
`MonotonicClock` стал `Copy`, `Peripheral` держит одни часы и копирует их в
каждый гейт, плюс запоминает unix-время своего нуля, чтобы монотонное смещение
можно было показать человеку. Видно в выводе: `+41089 мс` и `+100576 мс` вместо
двух нулей.

**IPC заполнен целиком, включая зарезервированное.** Commands:
`build_id`, `list_devices`, `connect_device`, `disconnect_device`,
`read_capability`, `journal`. Events: `device:connected`, `device:updated`,
`device:disconnected`, `device:protocol-error` (+ объявленный, но никем не
испускаемый `device:battery-changed`). Channels: `subscribe_analog_stream`
по-прежнему отказывает — и **тест на то, что аналоговый поток не подписан через
шину событий**, теперь есть.

`device:updated` — добавление к контракту. Обосновано: появление устройства и
изменение его состояния — разные новости, одно имя на оба делало бы имя ложным
в половине случаев, а фронтенд, принимающий каждое сообщение за появление,
растил бы дубликаты в списке.

**Контракт имён проверяется между языками.** `app/src-tauri/src/ipc/mod.rs`
читает `app/src/ipc.ts` через `include_str!` и падает, если имя команды или
события разъехалось в любую сторону. Причина: рассинхрон **молчит** с обеих
сторон — вызов несуществующей команды отклоняется в промис, который никто не
смотрит, а отправка события в имя, которое никто не слушает, **успешна**. Ни
то, ни другое не ломает сборку и оба выглядят как пустой экран. Сканер
игнорирует комментарии (и на этом сначала честно упал, поймав пример вызова из
прозы в doc-комментарии).

**Фронтенд: правила вынесены из компонентов.** `app/src/model.ts` — чистый
модуль без React, IPC и часов. Там живут `canRead`, `writeControlsEnabled`,
`valuesByLabel` и жизненный цикл прочитанных значений. Условие внутри компонента
— это условие, которое кто-нибудь скопирует в следующий компонент чуть иначе;
эти конкретные условия — те, чьё нарушение пользователь не заметит.

**Правило, которого в тикете не было, но которое пришлось ввести: значение не
переживает сессию, которая его прочитала.** Число, оставшееся на экране после
того как устройство выдернули или его endpoint залип, — это экран, тихо
сообщающий состояние железа, которое сейчас ничем не подтверждено. Реализовано
в `applyEvent`, проверено четырьмя тестами и на живом железе.

**Гейт по выбору клавиши.** `valuesByLabel` **отказывается** привязывать
значение к метке, которая в раскладке встречается дважды (`Shift`, `Ctrl`,
`Alt`). Иначе одно измерение печаталось бы под клавишей, которую никто не мерил
— правдоподобный неверный ответ, то есть тот же класс ошибки, за который проект
уже заплатил обменом 003, перепутав два пространства нумерации клавиш.

### Prior art

UX и архитектурные границы разобраны в `docs/prior-art/ui-prior-art.md`
(Pipette Desktop, OpenRGB, libratbag/Piper, Vial/Keychron Vial/QMK). Все четыре
copyleft, все в режиме `docs`, кода не взято. Pipette добавлена в
`inventory.md` — её там не было.

Самое полезное из разбора — не решение, а его отсутствие: **ни один из четырёх
не показывает, откуда известно, что число означает то, что означает.** Им это и
не нужно — у всех либо открытый протокол, либо полученный от производителя. У
нас протокол восстановлен и проверен на одной плате, поэтому `origin`,
`confidence`, имя команды и строка provenance рядом со значением — это то, чем
наш экран HE обязан отличаться от всех перечисленных.

### Дефекты, найденные и исправленные по ходу

1. **Кнопка Connect на устройствах без config-канала.** На обычной машине
   большинство HID-устройств такие, и ряд серых кнопок читается как сломанное
   приложение, а не как устройства, которые оно и не собиралось настраивать.
   Теперь кнопки нет вовсе. Залипшее устройство — обратный случай, там кнопка
   есть и она задизейблена: отсутствие действия нужно объяснить.
2. **Connect ухудшал структурную ось.** `connect()` из TICKET-12 пересчитывал
   идентификацию по **одной** коллекции (той, в которую говорил), и structural
   падал с `candidate` до `unknown`, а digest менялся. Обмен не может изменить
   форму устройства; наблюдение теперь строится по всем его коллекциям.

### Дефект, найденный и НЕ исправленный (вне scope)

**Байтовые размеры отчётов в реестре разъехались с транспортом на единицу.**
Структурная ось на всех трёх собственных устройствах проекта отдаёт `candidate`
вместо `verified`: `descriptor_digest` и `report_profile` — `Differed`.

Причина установлена точно. `ptransport::shape` считает размеры **включая байт
report id** (это осознанно и закреплено его же тестами), а `data/devices/*.toml`
хранят объявленный дескриптором payload **без** него. Поэтому каждая коллекция с
report id расходится ровно на единицу, а единственная коллекция AULA без report
id (`if0 0001:0006`, in=8 out=1) совпадает точно. Все семь `descriptor_fnv1a64`
совпадают — сами дескрипторы не менялись.

Почему не поймали раньше: `pregistry/tests/real_hardware.rs` гоняет захваченный
JSON через тот же путь, что и данные реестра, поэтому обе стороны согласны между
собой и расхождение с живым железом невидимо. Это ровно та ловушка, о которой
предупреждает лог TICKET-10 — регрессионный тест начал соглашаться с кодом
вместо железа.

Не исправлено здесь сознательно: выбор канонической величины — решение уровня
`pregistry`, генератор этих TOML вообще не закоммичен в `scripts/`, а править
fingerprint-данные внутри UI-тикета — тот самый дрейф scope, от которого
защищает процесс. Заведено отдельной задачей. **Влияния на безопасность нет:**
продуктовая ось по-прежнему `verified` по строкам и id, запись гейтится по оси
семейства, которая не затронута.

### Что осталось не зелёным

`cargo deny check advisories` падает на неподдерживаемых GTK3-биндингах,
приходящих транзитивно через Tauri. Было так до этого тикета; здесь добавлена
одна зависимость — `vitest` (MIT, devDependency фронтенда, в релизный бинарь не
входит).

## Deviations

1. **Экранов не три, а четыре.** Добавлен About. Причина не в желании: сборка
   читает четыре клавиши на одной плате и не пишет ничего, и человек, который её
   поставил, должен узнать это на экране, а не выяснить, исследуя интерфейс,
   который подразумевает больше.

2. **Rapid trigger не показан даже серым.** Тикет просил actuation/RT с пометкой
   `origin`. RT-команда не верифицирована, поэтому варианта под неё нет в
   `pcaps::CapId` — а он закрытый enum. Это **строже** формулировки спецификации
   («скрыта либо серая с пометкой»): выбран не первый вариант из двух, а третий
   — контролу физически не к чему привязаться. Появится вместе с командой.

3. **Connect — явное действие, а не автоподключение.** Тикет этого не оговаривал.
   Connect — это отправка команды, а config-endpoint может держать вендорский
   софт; политика проекта — детектировать и предупреждать, а не отбирать.
   Приложение, тянущееся к каждой появившейся плате, было бы второй стороной
   этой гонки.

4. **Детекция конфликта с вендорским софтом — подозрение, а не вывод.** Тикет
   разрешал «минимальную эвристику». Реализовано: канал есть, открыть не
   удалось → «вероятно, его держит другое приложение, закройте вендорский софт и
   попробуйте снова», и **без кнопки повтора**. Сильнее сказать нечем — backend
   отдаёт локализованный текст без кода (находка TICKET-08), поэтому
   *установить* причину нельзя. Типизированный `AccessDenied` дал бы больше; он
   ждёт ту же работу по классификации ошибок, что заблокирована в TICKET-15.

5. **Появился слой `pcore::service`, которого в тикете не было.** Обоснование —
   в Implementation notes: Tauri требует `Send + Sync` state, а мьютекс вокруг
   `Peripheral` — запрещённая FR10 форма. Полноценная `DeviceSession` из FR10
   по-прежнему за TICKET-15.

6. **Физическое отключение устройства не проверено.** Проверен разрыв сессии
   (Disconnect) на железе и логика диффа watcher'а — чистой функцией `departed`
   с четырьмя тестами, плюс четыре теста фронтенда на то, что значения не
   переживают устройство. Само выдёргивание кабеля требует человеческой руки:
   сессия не имеет прав администратора, а отключать пользовательскую клавиатуру
   через `Disable-PnpDevice` без его просьбы неуместно. Внесено в
   hardware-in-the-loop чеклист.

7. **Раскладка — placeholder, и говорит об этом на экране.** Обобщённая 75%
   раскладка на 82 клавиши, объявленная как «не прочитана с устройства и не
   проверена на нём». Тикет это прямо разрешает (SAFE_DEFAULT на импорт
   раскладок). Число 82 печатается из самих данных, а не подгоняется под 84
   клавиши платы: подгонка означала бы намёк, что раскладка совпадает с
   реальной.

8. **Два одинаковых устройства выглядят как одно.** Разделение по VID:PID — всё,
   что даёт перечисление. Различать их нужен либо идентификатор экземпляра
   (который политика проекта редактирует), либо платформенное чтение путей
   устройств; выдумывать эвристику под железо, которого у проекта нет и на
   котором её нельзя проверить, хуже, чем сказать прямо. Записано в шапке
   `pcore`.

9. **Добавлена зависимость `vitest`** (MIT) для фронтенд-тестов, которых тикет
   требует. devDependency, в релизный бинарь не входит.

10. **`device:updated` — новое имя события в контракте.** Обоснование в
    Implementation notes.

## Review findings

Самопроверка (у проекта нет второго рецензента; `/code-review` заменён ею по
установившейся практике). Блокирующих findings нет. Незакрывающие:

1. **Watcher переспрашивает перечисление, а не подписан на уведомления ОС.**
   Раз в 2 секунды, без обращения к устройствам, поэтому цена нулевая — но
   правильная форма для Windows это `WM_DEVICECHANGE`, а не опрос. Пока
   опрос не мешает; при появлении трея (TICKET-20) стоит пересмотреть.

2. **Rate limiter по-прежнему живёт на гейте, создаваемом на операцию.**
   Наследство TICKET-12, здесь не исправлено и не могло быть: каденция между
   операциями не отслеживается. Закроется вместе с настоящей `DeviceSession` в
   TICKET-15.

3. **Kill-switch на живом железе не срабатывал ни разу**, потому что stall ни
   разу не случился. Путь «stall → карантин → экран с инструкцией без кнопки
   повтора» проверен только тестами (`failure_view`). Синтетика.

4. **Структурная ось деградирована** — см. отдельный раздел в Implementation
   notes; заведено задачей, к этому тикету не относится.
