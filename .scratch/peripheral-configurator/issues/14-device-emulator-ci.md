# TICKET-14: `tools/emu` device emulator + первый CI-тест fingerprint→family

## Status

DONE_WITH_DEVIATIONS (2026-08-18)

## Objective

Собрать `tools/emu` из записанных ответов AULA Hero 84 HE (полученных в TICKET-08/12) и поставить первый CI-тест "fingerprint → ожидаемое семейство", чтобы CI не зависел от физического железа на раннере.

## User or system value

Без эмулятора CI не может проверять протокольную логику вообще — hardware-in-the-loop не масштабируется на CI-раннеры. Это прямое условие Test seams из `spec.md` ("Device emulator — единственный способ иметь CI без физического железа").

## Dependencies

TICKET-08 (нужны реальные записанные ответы устройства), TICKET-10 (fingerprint matcher, который тест проверяет).

## Scope

- `tools/emu`: подставной HID-девайс за тем же `ptransport`-контрактом (`DeviceSession`/`SessionHandle` по `DeviceId`, не голый handle — см. architecture review §6/§9), воспроизводящий записанные ответы AULA.
- Функция "врать как настоящий": на неизвестный/неподдержанный опкод возвращает предыдущий ответ (не ошибку) — воспроизводит задокументированное поведение реальных плат (§0 плана, "reply is not evidence").
- CI-тест: эмулированное устройство → `pregistry` matcher → ожидаемый `confidence: verified` и правильная `protocol_family`.

## Out of scope

- Эмуляция второго устройства — добавляется отдельным follow-up, когда remote-валидация (TICKET-09) даст реальный артефакт. Этот тикет ею **не блокируется**. До тех пор роль «структурно другого устройства» в тестах играет синтетический профиль, а не запись живой платы, и это ограничение фиксируется явно.
- Fuzzing report descriptor парсера — упомянуто в Test seams `spec.md`, но отдельный follow-up, не входит в это тикет.

## Acceptance criteria

- [x] `tools/emu` запускает подставное устройство, отвечающее записанными пакетами AULA.
- [x] `ptransport`/`pregistry`/protocol-engine код из TICKET-10/12 работает против эмулятора **без изменений** (это и есть проверка, что абстракция `ptransport` не завязана на реальное железо).
- [x] CI-тест "fingerprint → family" зелёный на всех трёх ОС без физического устройства.
- [x] Эмулятор корректно воспроизводит "неподдержанная команда → предыдущий ответ" (регрессионный тест на анти-фикция-сценарий).

## Verification plan

`cargo test -p emu` + CI на трёх ОС; ручная проверка, что тот же код пути (protocol engine из TICKET-12), направленный на эмулятор вместо реального устройства, даёт идентичный результат.

## TDD classification

REQUIRED (детерминированное поведение — "возвращает записанный ответ", "имитирует неподдержанную команду" — canonical TDD case).

## Expected architecture impact

Подтверждает (или опровергает) архитектурное решение TICKET-07/08 не завязывать `ptransport`-контракт на реальные Win32/hidraw типы — если эмулятор не может встать за тот же интерфейс без хаков, это сигнал, что абстракция протекает, и требует ревизии перед тем, как на неё будут писаться дальнейшие protocol engines.

## Risks

Нет существенных сверх обычных рисков тестовой инфраструктуры.

## Implementation notes

### Что реально сделано (2026-08-18)

Эмулятор построен не как «HID-эхо-сервер», а как второй реализующий транспортный
контракт объект — и именно это оказалось главной архитектурной проверкой тикета.

- **`ptransport::ReportChannel`** — новый трейт: `report_id`, `write_report`,
  `read_report`. `ProbeChannel` теперь реализует его, а не держит эти методы
  собственными. До этого тикета единственной реализацией был hidapi-backed
  `ProbeChannel`, то есть утверждение «крейт прячет ОС» никогда не проверялось.
- **`pproto::aula_bytech_io::Exchange<C: ReportChannel>`** стал генерик. Это
  единственное изменение в production-коде, потребовавшееся, чтобы движок
  заработал против поддельного устройства. Ни одного `#[cfg(test)]`, ни одного
  mock-хука, ни одного специального конструктора внутри production-крейтов.
- **`pemu` стал библиотекой + бинарником.** Библиотека даёт `FakeFirmware`,
  `EmulatedChannel`, `Aula84He` и `Topology`; бинарник печатает фикстуру, чтобы
  её можно было осмотреть глазами.
- **Байты записаны, а не вычислены.** Ответы взяты дословно из exchange-001/003/004.
  Фикстура, синтезирующая ответы нашим же энкодером, согласуется с нашим же
  декодером при любых убеждениях обоих и не способна их опровергнуть.
- **Ложь воспроизведена**: неизвестная команда повторяет предыдущий ответ;
  `read_travel_precision` возвращает запрос байт в байт; `Silence`; `Stall`,
  который не снимается ничем, кроме `reconnect()`.
- **Дефект exchange-004 воспроизводим без железа**: запрос, построенный из HID
  usage вместо `keyValue`, получает безупречно валидный ответ про четыре чужие
  клавиши.

Тесты (26 в `pemu`): production-путь чтения model id против несуществующего
устройства; отказ по чужому семейству, по неопознанному устройству и по
измеренному интервалу — все три до записи в устройство; квартин по stall и его
снятие только реконнектом; пропуск unsolicited-репортов; отказ декодера от
повторённого ответа; отказ от переставленного порядка ключей; fingerprint-регрессии
на реальном захвате, включая «структура не называет продукт» и «VID:PID не даёт
семейства».

CI: отдельный шаг `cargo test -p pemu` на всех трёх ОС, названный так, чтобы
негативное утверждение («железо не требуется») было видно в логе.

### Отклонения

1. **Эмулятор не поднимает настоящее HID-устройство в ОС.** Тикет говорил
   «подставной HID-девайс за тем же `ptransport`-контрактом». Контракт теперь
   существует явно (`ReportChannel`), и эмулятор стоит за ним — но виртуального
   узла в системе он не создаёт и `Hid::enumerate()` его не видит. Перечисление
   покрыто отдельно: топология разбирается из реального захвата TICKET-08.
2. **`DeviceSession`/`SessionHandle` не использованы**, потому что их всё ещё
   нет — их строит аналоговый стрим (TICKET-15), а не одиночный обмен.
3. **Второго семейства по-прежнему нет.** Роль «структурно другого устройства»
   играют вариации реального захвата, а не запись живой платы; ограничение
   зафиксировано в самом тикете и остаётся открытым риском.
