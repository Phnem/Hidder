## Implementation notes

Создан `docs/prior-art/royuan.md`: транспорт, семейства и правило их определения, две схемы контрольных сумм, полная опкод-таблица (общие / yc500 / gen2), список отвечающих и не отвечающих опкодов на плате X86, HE-слой, деструктивные опкоды, тайминги/rate limiting, форматы данных (слот раскладки, макросы, LED-параметры).

**Главная находка (меняет понимание задачи, не меняет тикеты):**

HE-блок опкодов в OEM-протоколе **существует** (`0x1B`–`0x1E` магнитные переключатели, `0x65`/`0x9C`–`0x9E` Rapid Trigger), но на плате Attack Shark X86 не отвечает — с маркером `[HW]`, т.е. это результат реальной попытки. При этом на Attack Shark X68 PRO HE (тот же VID `0x3151`) опкод `0x1B` рабочий и включает аналоговый стрим (данные из `he-analog-gamepad`, MIT). Отсюда вывод, которого в плане не было сформулировано явно: **отсутствие ответа — не доказательство отсутствия возможности**; это доказательство только про конкретную прошивку конкретной платы. Симметрично уже существующему правилу «ответ устройства — не доказательство». Внесено в `spec.md` § Domain rules (см. Deviations, пункт 2).

**Второй результат:** префикс включения аналогового режима у `he-analog-gamepad` — байт `0x1B`, тот же номер, что sharkfin числит опкодом магнитных переключателей, и тот же размер кадра 64 байта. Сильная гипотеза, что это один протокол. Не факт — проверяется в TICKET-09. Конкретный проверяемый вопрос для TICKET-08/09 записан в документе: одна ли это vendor-коллекция (usage page `0xFFFF`/usage `2`/report ID `0` у sharkfin) или разные (стрим приходит репортом ID `0x05`).

**Подтверждения наших доменных правил внешним источником** (все — новые свидетельства, ни одно правило не менялось):
- семейство определяется по реестру, **никогда** по product ID — прямо сформулировано в sharkfin и подтверждено масштабом (945/949 плат);
- опкоды коллидируют между семействами с разной семантикой — задокументированные примеры: `0x06` (Options у yc500 / Debounce у gen2), `0x09` (Keymatrix / Options), `0x11` (Debounce / таймеры сна), factory reset `0x02`↔`0x01`. Подтверждает, что `opcode_acl` обязан быть per-family (схема это уже предусматривает);
- превышение частоты записи → застревание endpoint'а с protocol error. Наш failure mode «stall → переподключи кабель» перестал быть предположением;
- rate limiting как свойство семейства: измеренные значения для ROYUAN — ~12 мс между репортами, ≤2 загрузки/10 с, 100 мс между страницами, 2 с settle.

**Практический вход для `pregistry` (TICKET-10):** безопасный identify-опкод для цепочки fingerprint — `0x8F` (возвращает `u32` LE идентификатор), версия прошивки — `0x80` (`(байт2<<8)|байт1`). Оба входят в список подтверждённо отвечающих на X86.

**Практический вход для TICKET-15:** включение аналогового стрима — это Feature Report (запись), а не чтение. Значит Analog Monitor не является исключением из FR2 и проходит через `SafeCommandId`.

## Deviations

1. **Scope чтения.**
   - **Planned:** «Чтение `docs/PROTOCOL.md` и исходников sharkfin».
   - **Actual:** прочитан и законспектирован `docs/PROTOCOL.md` (плюс метаданные коммита для пина версии); исходники Rust построчно не читались, `docs/BOARDS.md` не читался.
   - **Reason:** verification plan тикета — «документ достаточен, чтобы TICKET-09 мог начать Safe Probe на ROYUAN-плате без повторного чтения sharkfin». `PROTOCOL.md` этот критерий закрывает: транспорт, опкоды, контрольные суммы, тайминги, деструктивный список — всё оттуда. Чтение исходников добавило бы риск непреднамеренного заимствования выражения из GPL-кода при нулевом приросте фактов, что прямо противоречит режиму `facts` из ADR-0001.
   - **Consequence:** таблица соответствия VID:PID → 949 плат не перенесена. Она нужна не здесь, а в TICKET-05 (OEM-карта), и брать её надо как **данные** с отдельной проверкой лицензии на данные — зафиксировано в разделе «Чего в конспекте нет».
   - **Follow-up:** учтено в TICKET-05, новый тикет не требуется.

2. **Правка `spec.md` (мутация артефакта выше уровня тикета).**
   - **Planned:** тикет объявлен как «Expected architecture impact: нет прямого — это входной документ для `data/protocols/royuan.yaml`».
   - **Actual:** в `spec.md` § Domain rules добавлено правило-симметрия «отсутствие ответа — не доказательство отсутствия возможности».
   - **Reason:** это доменное открытие, а не деталь реализации, и оно получено именно из этого тикета. Без него следующий тикет (TICKET-09/10) имеет прямой стимул записать «у ROYUAN нет HE» на основании `[HW]`-факта об одной плате — то есть превратить «неизвестно» в «нет», что запрещено принципом «prefer explicit uncertainty».
   - **Consequence:** правило **additive** — ни одно acceptance criterion не ослаблено, ни один тикет не переупорядочен. Усиливает уже существующее требование анти-фикция-фильтра (FR5).
   - **Follow-up:** нет.
