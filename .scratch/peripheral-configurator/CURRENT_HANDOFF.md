### Что теперь невозможно обойти (TICKET-11)

- Опкод, помеченный `destructive`/`unknown` или не помеченный никем, **не имеет представления в программе**: варианта в `SafeCommandId` нет, а построить его из байта нечем — публичного пути «байт → команда» не существует.
- `SafeCommandId::opcode()` — `pub(crate)`. Байт читается ровно в одном месте: когда гейт выпускает `AuthorizedCommand` после всех проверок.
- `AuthorizedCommand` невозможно сконструировать снаружи и невозможно переиграть (не `Clone`, потребляется при dispatch).
- Гейт **владеет** sink'ом; у engine нет объекта, через который можно отправить что-то мимо. Batch-входа нет — одна команда за вызов.
- ACL keyed by family; команда чужого семейства отклоняется (`Refusal::WrongFamily`).
- Write-класс без записанного backup отклоняется.
- Тайминги только измеренные, из ACL-файла семейства; глобальных констант нет. Неизмеренное семейство → подтверждение на **каждую** операцию, `UserConfirmation` принимается по значению.
- Stall → карантин устройства, включая чтения; снимается только `device_reconnected()`. Ретраев нет нигде.

Состояние реестра: **16 команд, все read/probe, write-команд ноль. У `aula-hero84-he` — ноль команд вообще.**

### Что известно про AULA после инвентаря

VID `0x372E`, PID `0x103E`, строки `BY Tech` / `HERO 84 HE` (бренд AULA в строках устройства не фигурирует вообще). 7 top-level collections на 3 USB-интерфейсах, все открылись без прав администратора. **Два** vendor-TLC: `0xFF00:0x0001` (только feature-репорты, 64 байта) и `0xFF60:0x0061` (in/out по 64 байта). Какой из них конфигурационный и есть ли в них аналоговый поток — неизвестно, требует I/O.

Плата **не ROYUAN**: VID отсутствует в списке семейства, форма vendor-канала другая. Теперь это факт, а не предположение.

## Изменение плана 2026-08-17 (после TICKET-08): где теперь EPOMAKER

**EPOMAKER физически находится не у разработчика, а у стороннего владельца (отца пользователя).** Прогонять по ней developer-инструменты нельзя: установка Rust/cargo/Build Tools/USBPcap/скриптов на чужой компьютер противоречит цели продукта и не даёт product-level валидации.

Поэтому:

- **EPOMAKER больше не reference board.** Локальное железо — AULA Hero 84 HE и (с 2026-08-18) VXE Dragonfly R1 SE+.
- Новая роль EPOMAKER — **remote external validation device**: поздняя проверка более-менее готовой пользовательской сборки на неизвестном устройстве у постороннего человека. Она проверит сразу generic `ptransport`, `pregistry`/fingerprinting, безопасный Inventory/Export flow, редактирование серийника, поведение на неизвестном устройстве, отсутствие AULA-специфичных предположений, будущий Learning Mode Level 0 и удобство сценария без dev-toolchain.
- **TICKET-06 и TICKET-09** переведены в состояние `DEFERRED_REMOTE_VALIDATION` (не отменены). Порядок между ними развернулся: сначала **09** (артефакт от приложения), затем **06** (идентификация по артефакту + публичным источникам).
- **Гейт возврата — capability-based, не «после фазы N»:** нужна обычная Windows-сборка, которая безопасно перечисляет неизвестное устройство, ничего в него не пишет, генерирует versioned inventory-артефакт, сама редактирует серийник и показывает одну кнопку **Export**. Естественно — после TICKET-13/14 или как ранний безопасный Level 0 из TICKET-16, и не раньше, чем UX перестанет выглядеть как инженерный debug tool.
- **Заранее ничего не назначать:** ни второе protocol family, ни HE, ни ROYUAN, ни конкретный OEM, ни wireless. Только по данным.
- **`if epomaker { ... }` в транспорте запрещён.** Не справился generic `ptransport` — чинится абстракция, а не создаётся vendor-specific enumeration.

Это не ослабление плана: EPOMAKER стала более ценным тестом — репетицией community-submission на живом человеке.

## Что дал TICKET-22 (второе локальное устройство)

Снято два режима VXE Dragonfly R1 SE+ штатным инструментом, без единой строчки кода под устройство:

| | AULA | VXE ресивер | VXE кабель |
|---|---|---|---|
| VID:PID | `372E:103E` | `3554:F58E` | `3554:F58F` |
| strings | `BY Tech` / `HERO 84 HE` | `Compx` / `VXE Mouse 1K Dongle` | `Compx` / `VXE R1SE+` |
| release | `0x0216` | `0x0110` | `0x0315` |
| интерфейсы / TLC | 3 / 7 | 3 / 8 | 3 / 8 |
| vendor-TLC | 2 (по 64 байта) | 4 (17/8/8/8) | те же 4 |
| battery usage | нет | нет | нет |

**Главная находка — про модель fingerprint'а, а не про мышь.** Ресивер и сама мышь отдают побайтово одинаковые дескрипторы: все восемь коллекций, те же report ID, размеры и все восемь хешей. Различаются ровно три поля: PID, product string, release.

Спецификация ранжирует сигналы: хеш дескриптора → TLC → строки → identify → fw → VID:PID («слабейший»). Здесь **порядок перевёрнут**: два сильнейших не различают ресивер и мышь вообще, различают ровно три слабейших. Вывод не «ранжирование неверно», а «неполно»: сильные сигналы отвечают «что это за устройство по форме», слабые — «с каким физическим предметом я разговариваю». Это прямая задача TICKET-10, занесена в его acceptance criteria и в риск-регистр.

Вторая находка: **ресивер — самостоятельное HID-устройство.** Три захвата в трёх состояниях мыши (работает по радио / на кабеле / выключена) не отличаются ни одним полем. Он показывает mouse- и keyboard-коллекции и четыре vendor-канала независимо от наличия мыши. Точная формулировка важна: **отдельного enumerated HID device** за ресивером не появляется — это утверждение о перечислении, а не об адресуемости, и удалённая периферия вполне может быть адресуема через vendor-протокол ресивера (не проверялось, проверка = отправка). Следствие для UI: список устройств из одного перечисления покажет донгл как всегда присутствующую мышь.

**Bluetooth не получен и не опровергнут.** BT-позиция переключателя есть, спарить не удалось; BT-стек хоста при этом рабочий (с ним спарены другие устройства), поэтому дело не в отсутствии радио. Записано как inconclusive — утверждение «этот экземпляр BT не поддерживает» сознательно не сделано. Если позже спарить удастся, в сравнительный артефакт добавляется четвёртый столбец.

Побочно: generic `ptransport` впервые отработал на устройстве **другой категории** и не потребовал ни одного изменения.

### Слои, которые теперь есть

- **`pproto::aula_bytech_*`** — движок семейства. Протокол восстановлен
  статически из вендорского бандла, без исполнения его кода. Команда этого
  семейства — пара (group, subcommand), не голый байт.
- **`psafety::ProbeGate` / `bootstrap_probe`** — отдельная дверь для первой
  отправки команды, у которой ещё нет hardware-evidence. Сейчас **пуста**, и это
  установившееся состояние: обе команды прошли через неё и вышли в
  противоположных направлениях (одна в `safe_read`, другая в `unknown`).
- **`pcore::service::DeviceService`** — один поток владеет `Peripheral`, ручка
  `Send + Sync`. **Не** `DeviceSession` из FR10; та строится в TICKET-15.
- **`pcore::model`** — снимки для UI. Ни одного пути устройства, ни одного
  байта опкода; каждое различие, на котором настаивает спецификация («нет
  верифицированной команды» / «железо этого не имеет» / «ещё не читали»), —
  отдельный вариант, а не `null`.
- **`tools/emu`** — вторая реализация `ReportChannel`, врущая как настоящая
  прошивка (повтор предыдущего ответа, эхо запроса, молчание, stall).
- **`app/`** — четыре экрана: Devices, HE, Journal, About.

### Что теперь невозможно обойти (добавление к списку TICKET-11)

- **UI не может назвать capability, которой нет.** `pcaps::CapId` — закрытый
  enum с одним вариантом. Контролу rapid trigger физически не к чему
  привязаться: правило «никогда не показывать контрол без подтверждённой
  команды» держится типом, а не разметкой и не дисциплиной.
- **Имена IPC проверяются между языками.** `include_str!` на `app/src/ipc.ts` +
  тесты в `ipc/mod.rs`: имя команды или события, разъехавшееся в любую сторону,
  роняет сборку. До этого рассинхрон был бы **молчаливым** с обеих сторон.
- **Аналоговый поток не может незаметно поехать через шину событий** — есть
  тест, который это ловит.
- **Значение не переживает сессию, которая его прочитала.**

## Открытый дефект, заведённый TICKET-13 (не блокирует TICKET-15)

**Данные реестра и транспорт считают размеры отчётов по-разному, ровно на один
байт.** `ptransport::shape` считает **включая** байт report id (осознанно,
закреплено его тестами), `data/devices/*.toml` — **без** него. Следствие:
структурная ось на всех трёх собственных устройствах отдаёт `candidate` вместо
`verified`. Все `descriptor_fnv1a64` совпадают — дескрипторы не менялись.

Почему не поймали раньше: `pregistry/tests/real_hardware.rs` гоняет захваченный
JSON через тот же путь, что и данные реестра, поэтому обе стороны согласны между
собой. Регрессионный тест начал соглашаться с кодом вместо железа — ровно то, о
чём предупреждает запись TICKET-10, и предупреждение не спасло.

Безопасности не касается: продуктовая ось `verified` по строкам и id, запись
гейтится по оси семейства. Требует отдельного решения в `pregistry`: какая
величина каноническая, перегенерация TOML, **коммит генератора** (его нет в
`scripts/`) и проверка, падающая при деградации `verified` → `candidate`.

## Decisions that must be preserved

Решения пользователя (не переспрашивать):

1. Лицензия — proprietary; GPL-проекты только как источник фактов и методов, не кода.
2. Sharkfin — независимая разработка; контакт с автором ради обмена информацией. Изучение его исходников разрешено пользователем явно (2026-08-17) и не отменяет ADR-0001.
3. Позиционирование — HE-first в маркетинге, universal в архитектуре.
4. Локальное железо — **AULA Hero 84 HE** (проводная клавиатура) и **VXE Dragonfly R1 SE+** (беспроводная мышь с 2.4 ГГц ресивером, вариант `44857375424730`, добавлена 2026-08-18) (не ROYUAN: покупка отменена 2026-08-17; не EPOMAKER: она у стороннего владельца). Принадлежность EPOMAKER к какому-либо protocol family **не предполагается** — её устанавливают данные удалённого инвентаря, и вывод по бренду прямо запрещён.
5. Установка Rust-тулчейна на машину разработчика — разрешена и выполнена. **На чужом компьютере не устанавливается ничего, кроме обычной сборки Peripheral.**
6. Phase 2 сведена к выполненному TICKET-08; TICKET-05 — параллельный research track; TICKET-06/09 — remote-validation track; фаза 5 называется «Second protocol family» — какое семейство станет вторым, решают данные, а не план.
7. Порядок основного code path: TICKET-11 → 10 → 12 → 13 → 14 → 15 → 16. Safety-граница раньше первого engine.

Архитектурные решения: `hidapi` как основная транспортная абстракция; handle владеется исключительно `DeviceSession` в выделенном worker-потоке; IPC — три механизма Tauri, Channels обязательны для аналогового стрима; крейты образуют однонаправленный DAG.

Отложено в архитектурный чекпоинт (не править сейчас, но и не потерять): формулировка FR10 (`DeviceSession` владеет **набором** handle'ов — `CollectionHandleSet`; инвариант «handles не покидают `ptransport`» сохраняется), нужна ли platform-native классификация ошибок вместо текстовых `hidapi`, различие «enumeration access ≠ usable read/write channel». Повестка — в `MASTER_PLAN.md`.

Жёсткие запреты: никакой прошивки в v1; `tools/ingest` вне релизной сборки; запись только через `SafeCommandId`; `confidence < Verified` → read-only; никогда не показывать контрол без подтверждённой команды.

Доменные правила, добавленные в фазе 1: отсутствие ответа устройства — не доказательство отсутствия возможности; настройка, переживающая выключение питания, — это flash-запись, и её класс задаёт интервал до и тишину после; второй экземпляр приложения не запускается; stall останавливает и фоновый опрос.

Добавлено после TICKET-08: **идентификаторы экземпляра устройства редактируются по умолчанию** — в любой передаваемый артефакт попадает `serial present: true`, а не значение. Политика общая, не AULA-специфичная.

## Known failures or blockers

**Блокеров для TICKET-15 нет** в смысле «нельзя начать». Есть три вещи, которые
он обязан решить внутри себя, и одна из них — настоящий блокер записи.

1. **Классификация ошибок транспорта — блокер записи.** `hidapi` отдаёт
   локализованное сообщение без кода; kill-switch (FR3) реагирует **только** на
   типизированный `EndpointStalled`, а транспорт его нигде не производит. За
   весь read-only путь это ни разу не сработало против нас — потому что stall'а
   ни разу не случилось, а не потому что он обработан. Писать в устройство без
   работающего kill-switch нельзя.
2. **Последний участок пути держится на соглашении, а не на типах.**
   `ptransport` не имеет write-API; когда он появится, он обязан принимать
   только то, что произвёл `SafetyGate`. Нужна механическая проверка — типами
   текущего DAG это не выражается.
3. **`DeviceSession` из FR10 не построена.** Каждое чтение открывает канал
   заново, поэтому rate limiter живёт на гейте, создаваемом на операцию, и
   каденция между операциями не отслеживается. Аналоговому стриму нужна сессия
   с worker-потоком.

Открытые пункты, не блокирующие работу:

- **Расхождение реестра и транспорта на один байт** — см. отдельный раздел выше.
  Структурная ось деградирована до `candidate`; безопасности не касается.
- Создание remote-репозитория (для реального прогона CI) — требует решения
  пользователя: публикация кода проприетарного проекта. **CI не исполнялся ни
  разу.**
- **Второго protocol family по-прежнему нет.** Мышь дала вторую topology, но не
  второй протокол; эмулятор собран из записей самой AULA и потому не способен
  опровергнуть AULA-специфичные предположения. Риск «архитектура валидирована на
  одном protocol family» (риск №3 architecture review, premature trait
  finalization) остаётся открытым и обязан быть виден на архитектурном ревью.
  TICKET-14 его **не** закрыл и не мог.
- **Физическое отключение устройства не проверено** (нет прав администратора; см.
  Deviations 6 в `issues/13-*.md`). Логика диффа вынесена в чистую функцию и
  покрыта тестами, разрыв сессии проверен на железе, само выдёргивание кабеля —
  в hardware-in-the-loop чеклист.
- **Stall ни разу не случился на живом железе.** Путь «stall → карантин → экран
  без кнопки повтора» проверен только синтетикой.

## Exact recommended next action

**TICKET-15.** Verified write + Analog Monitor.

Порядок внутри тикета не свободен — первым идёт то, без чего запись небезопасна:

1. **Типизировать `EndpointStalled` в транспорте.** До этого kill-switch не
   работает, а без работающего kill-switch запись не начинается. Здесь же
   решается отложенный с TICKET-08 вопрос, нужна ли platform-native
   классификация ошибок (Win32 escape hatch внутри `ptransport`).
2. **Построить `DeviceSession` из FR10** — владение handle'ами на своём
   worker-потоке, очередь по `DeviceId`. Это заодно чинит каденцию между
   операциями и даёт аналоговому стриму то, чего у него сейчас нет.
3. **Механическая проверка, что raw HID write вызывается только из разрешённого
   адаптера.**
4. Только потом — первая write-команда в ACL и `Verification` через readback или
   аналоговый стрим.

Предупреждения, всё ещё релевантные:

- `opened = true` означает только доступ уровня перечисления. Не повышать
  confidence на этом основании.
- **Ответ устройства — не доказательство.** Неподдержанная команда часто
  повторяет предыдущий ответ; поэтому `Verification` не имеет варианта «устройство
  сказало ОК» и не должен его получить.
- Второго protocol family по-прежнему нет.
- Аналоговый поток — **через Channels, не через шину событий**. Есть тест,
  который это проверяет; он не декорация.
