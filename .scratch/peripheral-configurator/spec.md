# Peripheral (`peripheral-core`) — канонический спецификация v1

Источник: `peripheral-configurator-plan (1).md` v0.2 + интервью от 2026-08-17 (см. `EXECUTION_LOG.md`).
Кодовое имя: `peripheral-core` (нейминг продукта остаётся открытым вопросом — DEFERRED).

## Problem

Владельцы дешёвых китайских Hall-Effect (HE) клавиатур (AULA, MCHOSE, Attack Shark, AJAZZ, Womier, IROK, ROYUAN-семейство и др.) вынуждены пользоваться вендорским web/Electron-драйвером: кривой перевод, работает только в Chrome и/или только на Windows, теряет профиль при обновлении, не даёт единого пресета на клавиатуру+мышь разных брендов. Слой «keymap + RGB + макросы» на самой массовой платформе (ROYUAN) уже закрыт открытым проектом sharkfin — но HE-специфичный слой (actuation, Rapid Trigger, DKS, SOCD, калибровка, аналоговый стрим) в нём не отвечен прошивкой и остаётся незанятой нишей.

## Desired outcome

Локальный кроссплатформенный (Windows/Linux/macOS) конфигуратор, который:
- сам определяет модель HE-клавиатуры (и в перспективе — мыши) через многосигнальный fingerprinting, без ввода пользователя;
- читает и пишет HE-параметры (actuation, Rapid Trigger, dead zone, DKS, SOCD, tap-hold, калибровка) с обязательной верификацией записи, а не по факту «устройство ответило успехом»;
- даёт единый кросс-брендовый игровой пресет на разнородные устройства;
- работает полностью офлайн, без аккаунта, без обязательной телеметрии;
- продаётся как закрытое коммерческое приложение (см. ADR-0001), не полагаясь на GPL-код.

## Current behavior

N/A — greenfield-проект, кода не существует (см. `EXECUTION_LOG.md`, codebase discovery).

## Required behavior

### v1 scope (из исходного плана §1.2, подтверждено на интервью)

1. Определение устройства без участия пользователя (multi-signal fingerprint, §6.2 плана).
2. Чтение и запись HE-параметров: actuation point, Rapid Trigger (down/up/continuous), dead zone, калибровка, DKS, SOCD/null-bind, tap-hold.
3. Keymap, слои, макросы, RGB — по мере покрытия протокола (не блокирует v1 relies, но входит в capability-модель с первого дня).
4. Аналоговая телеметрия: живой график хода клавиши (demo-фича и одновременно инструмент верификации записи).
5. Профили: приложение → устройства; кросс-брендовые игровые пресеты.
6. Learning/Debug Mode для неизвестного железа — 4 уровня (Inventory → Guided Capture → Safe Probe → Verified Write), см. §8 плана.
7. Полностью офлайн, без аккаунта.

### Явно НЕ в v1 (§1.3 плана, без изменений)

- Прошивка (flash) устройства — никогда в v1.
- Свой ядерный/фильтр-драйвер Windows.
- Клауд, аккаунты, телеметрия по умолчанию.
- RGB-«канвас» на весь ПК (территория OpenRGB/SignalRGB).
- Гарнитуры/DAC/микрофоны — только задел в модели данных.

## User-visible behavior

- **Devices** — карточки устройств, статус подключения, детекция конфликта с запущенным вендорским софтом за config-endpoint.
- **HE** — главный экран: визуальный layout, множественный выбор клавиш, слайдеры actuation/RT с миллиметровой шкалой, live-превью.
- **Analog Monitor** — осциллограф хода клавиш в реальном времени.
- **Profiles** — пресеты, привязка к процессам (opt-in whitelist watcher), import/export.
- **Keys / Lighting / Macros** — по мере покрытия протокола.
- **Learning Mode** — отдельный «инженерный» раздел.
- **Journal / About** — журнал записей в устройство, происхождение знания о модели, лицензии.
- **System Tray** (добавлено 2026-08-17) — постоянная иконка в системном трее (Windows notification area / macOS menu bar / Linux status notifier — единый Tauri 2 `TrayIcon` API на все три ОС). ЛКМ по иконке открывает компактную quick-панель со списком подключённых устройств (имя, тип подключения `dev.connection`, заряд `dev.power.battery` если применимо), без открытия полного окна приложения. Настройки (`Settings → Tray`): режим самой иконки (иконка приложения / заряд устройства с наименьшим % / выбранное вручную устройство / скрыть), поведение клика (quick-панель / открыть полное окно), пороги предупреждений о низком заряде (дефолт: 20%, 10% — SAFE_DEFAULT, изменяемо).
- Дизайн-принцип (жёсткое требование, не пожелание): **никогда не показывать контрол, за которым нет подтверждённой команды.** Неподтверждённая capability — либо скрыта, либо серая с пометкой «не подтверждено на этой модели», за отдельным флагом «эксперименты».

## Domain rules

Терминология наследуется из `libhmk`/`minipad` как канонической (см. Глоссарий плана §19.3):

- **Protocol family** — набор устройств, говорящих одинаковыми опкодами. Не совпадает ни с брендом, ни с VID:PID.
- **PID переиспользуется вендорами** — семейство никогда не выводится только из VID:PID; матчинг многосигнальный с explicit confidence (§6.2 плана): report-descriptor hash → TLC-набор → manufacturer/product strings → safe identify-опкод → fw-версия → VID:PID (слабейший сигнал, только индекс).
- **Ответ устройства — не доказательство.** Неподдержанная команда часто возвращает предыдущий ответ или правдоподобную фикцию. Каждая capability имеет `origin`: `Verified(hw)` / `FromFirmware` / `FromVendorJs` / `Assumed` / `Unsupported`.
- **Отсутствие ответа — тоже не доказательство** (добавлено 2026-08-17 по итогам TICKET-01). Опкод, не отвечающий на конкретной плате, доказывает только то, что **эта прошивка этой платы** его не реализует — не то, что возможности нет у семейства. Подтверждённый случай: sharkfin фиксирует с маркером `[HW]`, что HE-опкоды `0x1B`–`0x1E` и `0x65`/`0x9C`–`0x9E` не отвечают на Attack Shark X86, тогда как на Attack Shark X68 PRO HE (тот же VID `0x3151`) опкод `0x1B` рабочий и включает аналоговый стрим (см. `docs/prior-art/royuan.md`). Следствия: (а) результат probe пишется в реестр как факт о **плате+прошивке**, никогда как факт о семействе; (б) `Unsupported` требует того же уровня доказательства, что и `Verified(hw)`, и не выводится из тишины устройства; (в) анти-фикция-фильтр (FR5) понижает гипотезу, а не отбрасывает её.
- **Опкоды внутри одного OEM-семейства могут коллидировать между суб-версиями протокола** — опкод, пишущий keymap в одной, может писать options-битфилд (в т.ч. бит полной блокировки клавиатуры) в другой. Отсюда: **писать можно только при `confidence >= Verified` для конкретной protocol_family**, иначе read-only.
- **Существуют деструктивные опкоды** (erase flash, вход в bootloader) — они физически не транслируются в исполняемую команду в production-сборке (см. Functional requirements, `SafeCommandId`).
- **Критерий «это flash-запись»: настройка переживает выключение питания** (добавлено 2026-08-17, TICKET-21). Как параметр выглядит в UI, значения не имеет: слайдер яркости подсветки выглядит как volatile-регистр, а является записью в flash, потому что сохраняется между включениями и стирается factory reset'ом вместе с раскладками. Класс записи задаёт **два** параметра, а не один: минимальный интервал перед следующей операцией и обязательную тишину **после** — тишина есть свойство совершённой записи, не следующей. Эмпирика по ROYUAN: плата залипала после 39 записей подсветки с интервалом 1 с, формально не нарушая ни одного порога, рассчитанного «как для регистра» (см. `docs/prior-art/sharkfin-methods.md`).
- **Rate limiting — свойство protocol family, не глобальная константа.** У известного семейства — измеренные на железе интервалы в `quirks`; у нового/неизвестного семейства — без дефолтного троттлинга, вместо этого одна запись за раз с явным подтверждением пользователя перед каждой следующей.
- **Идентификаторы экземпляра устройства редактируются по умолчанию** (добавлено 2026-08-17, обобщение находки TICKET-08 на весь продукт). Серийный номер и любые другие поля, идентифицирующие конкретный экземпляр, а не модель, **не нужны для fingerprinting** и потому не попадают ни в один артефакт, который человек может кому-то передать (device report, `.heprofile`, community submission, диагностический журнал). Записывается факт, а не значение:

```text
serial present: true
serial value:   REDACTED
```

  Сырой серийник допустим только при явном debug/export opt-in, если такая необходимость вообще возникнет. Политика общая, не привязанная к конкретному устройству или семейству: артефакты, которые предполагается передавать разработчику или в сообщество, обязаны быть безопасны по построению, а не по внимательности пользователя.
- **`dev.power.battery` не имеет единого источника.** У части устройств — стандартный HID usage `Battery Strength` (USB HID Usage Tables, Power Device page); у большей части китайской игровой периферии — собственный вендорский опкод (`GET_BATTERY`); у устройств на ресивере — команда самого ресивера (`GET_DEVICE_STATUS(device_index)`), не устройства напрямую. Capability Layer обязан скрывать это различие: `ProtocolEngine`/`ReceiverMouse` возвращают единый `BatteryState { percent, charging }` независимо от происхождения; UI и Tray никогда не знают, каким путём получено значение.

## Functional requirements

Capability-модель (§4 плана) — единый словарь, UI не знает про вендоров. Ключевые группы: `he.*` (actuation, rt.*, deadzone.*, calibration, dks, socd, taphold, analog_stream), `kb.*` (keymap, layers, macro, polling, debounce, sleep), `light.*`, `mouse.*` (заложено в модель, реализация — Phase 6), `dev.profiles`, `dev.power.*`/`dev.connection` (заряд и тип подключения — общие для любого wireless-устройства, не только мыши). Полная таблица — Приложение A (перенесена из исходного плана §4 с одним изменением от 2026-08-17: `mouse.battery` обобщён в `dev.power.*`, добавлен `dev.connection` — см. таблицу).

Архитектурные требования (детали — `architecture/INITIAL_REVIEW.md`):

- **FR1.** `ProtocolEngine` — единый trait для всех протоколов (`probe`, `capabilities`, `read`, `write`, `verify`, `stream`); `verify` обязателен для каждой capability, не опционален.
- **FR2.** Исполнитель записи в production-сборке принимает только `SafeCommandId` — закрытый enum, генерируемый на этапе сборки из записей реестра с классом ≠ `destructive`/`unknown`. Сырой opcode из БД/YAML не может дойти до транспорта без пересборки бинаря.
- **FR3.** `psafety`: ACL опкодов (safe_read/safe_write/probe_ok/slow_flash/destructive/unknown, дефолт — `unknown` = запрещено), rate limiter per-family/per-opcode-class, обязательный backup перед первой записью, журнал всех записей, kill-switch на `Protocol error` (без ретрая).
- **FR4.** `pregistry`: SQLite, сгенерированный из human-editable YAML (`data/devices/*.yaml`); схема — Приложение B (перенесена из §6.1 плана без изменений); многосигнальный matcher с explicit confidence (§6.2 плана).
- **FR5.** `plearn`: 4 уровня — Inventory (0, всегда безопасно) → Guided Capture (1, с патч-сценарием diff по ≥3–4 точкам, не по двум) → Safe Probe (2, allowlist только, обязательный анти-фикция-фильтр: повтор предыдущего ответа = «не поддержано») → Verified Write (3, backup → dry-run → одна запись → подтверждение НЕ по ответу устройства, а по readback/аналоговому стриму/физической проверке/визуально). Экспорт `.heprofile` (структура — §8 плана) с приватность-фильтром (ни один keystroke не попадает в capture-лог).
- **FR6.** `pprofile`: capability-graceful degradation при применении пресета; hardware-профиль (onboard slot) предпочтителен software-профилю, если поддержан; process watcher — отдельный opt-in поток с whitelist, без сканирования всех процессов.
- **FR7.** Транспортный слой строится на **`hidapi`** как основной кроссплатформенной HID-абстракции (Windows: `hid.dll`/Win32 HID backend; Linux: `hidraw` backend + udev-правила; macOS: `IOHIDManager` backend) — не на трёх независимых платформенных реализациях с нуля. Прямые платформенные вызовы (`HidD_*`, нативный `IOHIDManager` и т.п.) допускаются **только как escape hatch внутри `ptransport`**, когда конкретная возможность не покрывается `hidapi` (например, специфичные feature report edge cases). WinRT `Windows.Devices.HumanInterfaceDevice` не используется ни в каком виде. Конкретная доступность vendor-defined TLC на реальных платах — не факт, а гипотеза до наблюдения на железе (TICKET-08 — AULA; TICKET-09 — remote-артефакт EPOMAKER).

  > **Две находки TICKET-08, зафиксированные к рассмотрению на архитектурном чекпоинте** (2026-08-17; ни одна не исправляется сейчас):
  >
  > 1. **Текстовых ошибок `hidapi` недостаточно для machine-readable детекции stall'а.** Сообщение приходит без кода, а на Windows — локализованное ОС; определение stall'а по подстроке (как в prior art) на локализованной системе молча не срабатывает, то есть kill-switch FR3 просто не сработает. Win32 escape hatch **сейчас не реализуется**: инвентарь его не потребовал, и вводить платформенный код без нужды не следует. Вопрос возвращается при первом настоящем I/O (TICKET-12/15) — тогда и решается, нужна ли platform-native классификация ошибок (`EndpointStalled`/`AccessDenied`).
  > 2. **`opened = true` — это доступ уровня перечисления, а не пригодный read/write-канал.** Windows-backend при отказе в правах открывает устройство с нулевым доступом, и различить это можно только обменом. Никакой слой не вправе повышать confidence на том основании, что коллекция открылась для чтения метаданных.
- **FR8.** Learning Mode / capture обязаны фильтровать input-коллекции клавиатуры на уровне кода — приватность обеспечивается поведением, не только формулировкой в README; см. Test seams.
- **FR9.** `tools/ingest` — отдельный workspace-мембер, физически не входящий в релизную сборку и не публикуемый.
- **FR10.** Физический HID handle (`hidapi::HidDevice` или escape-hatch платформенный тип) никогда не покидает `ptransport` и никогда не используется напрямую верхними слоями — даже как "opaque handle", которым кто-то ещё может владеть. Каждое устройство представлено **одной `DeviceSession`**, которая единолично владеет физическим handle и выполняет блокирующий HID I/O (read/write/get_feature_report) в собственном выделенном worker-потоке; верхние слои (`pproto`, `pcore`) общаются с сессией через асинхронную command queue по `DeviceId`/`SessionHandle`, не получая доступа к handle напрямую. Причина: `hidapi::HidDevice` — `Send`, но не `Sync`, а HID-чтение может блокировать поток; без этой границы верхние слои неизбежно скатятся к mutex-обёртке вокруг одного handle с конкурентными read/write/get_feature_report.

  > **Уточнение отложено в архитектурный чекпоинт** (2026-08-17, находка TICKET-08; текст FR10 намеренно не правится до чекпоинта, чтобы не менять канон по одному наблюдению). Реальное устройство: 1 физическая периферия → 3 USB-интерфейса → 7 TLC → потенциально несколько одновременно нужных handle'ов (конфигурация через одну коллекцию, аналоговый стрим через другую). Формулировка «одна сессия владеет физическим handle» неточна: сессия владеет **набором** handle'ов — `DeviceSession owns CollectionHandleSet` или эквивалент. Главный инвариант при этом сохраняется без изменений и пересмотру не подлежит: **handles никогда не выходят из `ptransport`**, и I/O по каждому идёт в своём worker'е.
- **FR11.** IPC между UI и `pcore` в Tauri — три отдельных механизма, не один общий "typed IPC":
  - **Commands** (request/response) — для операций вида `get_config`/`set_actuation`/`connect_device`;
  - **Events** — для редких низкочастотных уведомлений (`device_connected`, `battery_changed`, `protocol_error`);
  - **Channels** (Tauri 2 ordered high-throughput streams) — обязательны для любого высокочастотного упорядоченного потока, в первую очередь `he.analog_stream` (Analog Monitor, до 84 клавиш × 100–1000 Hz) и capture/debug-потоков Learning Mode. Обычный event bus **не используется** для этих потоков — Tauri документирует, что async event listeners могут обрабатывать события не по порядку, что для аналогового стрима недопустимо.
- **FR12** (добавлено 2026-08-17). **System Tray**: `pcore`/`app` использует штатный Tauri 2 `TrayIcon` API (единый на Windows/macOS/Linux). Иконка-по-умолчанию рендерится **в памяти** (RGBA-буфер, 16/20/32 px), не хранится как набор PNG на каждое значение процента — обновление иконки (`tray.set_icon(...)`) происходит при реальном изменении `dev.power.battery` или не чаще, чем раз в 30–60 секунд (polling заряда не оправдывает более частого обновления). Логика выбора отображаемого значения: «иконка показывает наименьший заряд среди подключённых wireless-устройств» (SAFE_DEFAULT, настраивается в Settings → Tray). Рендеринг иконки — ответственность UI/`app`-слоя, не `pcore`: core-крейты отдают только `BatteryState`, ничего не знают про 16×16 RGBA-растры.

## Non-functional requirements

- Полностью офлайн; ни один сетевой вызов не требуется для базовой конфигурации устройства.
- Инсталлятор — target-оценка 20–60 МБ (§6.3 плана; помечено как **не измеренный факт**, пересчитать после первой сотни device definitions).
- CI на трёх ОС с первого дня workspace (см. TICKET-07).
- Зависимости — только permissive-лицензии (MIT/Apache-2.0/BSD/ISC), enforced лицензионным линтером в CI (см. ADR-0001).
- Локализация: EN-first + RU локализация с первого релиза (SAFE_DEFAULT, из §17.16 плана).

## Compatibility and migration constraints

- Нет заявленной обратной совместимости — проект greenfield, миграций из предыдущих версий не существует.
- Формат `.heprofile` и device-definition YAML должны быть версионированы с первого релиза (не деталь для v2 — иначе первые community submissions станут несовместимы с последующими схемами).
- Вендорский софт может одновременно держать config-endpoint устройства — приложение обязано детектировать конфликт, не пытаться захватывать endpoint силой (иначе риск stalled endpoint при percussive flash writes).

## Failure and fallback behavior

- `confidence < Verified` для protocol_family → устройство открывается **только в read-only режиме** с явным предложением Learning Mode; никаких «предположительных» контролов записи в обычном UI.
- Неподдержанный или не отвечающий опкод (по анти-фикция-фильтру Learning Mode) → гипотеza понижается, не автопринимается.
- `Protocol error` в процессе записи → сессия немедленно закрывается, показывается инструкция пользователю, автоматического ретрая нет (kill-switch, FR3).
- Config-endpoint не отвечает после серии flash-записей (stall) → понятная ошибка «переподключи кабель», не тихий зависон.
- Гонка за устройство с вендорским софтом → предупреждение и отказ от одновременной работы, не попытка форсированного захвата (см. §17.10 плана, SAFE_DEFAULT: детектить и предупреждать).
- **Второй экземпляр самого приложения не запускается** (добавлено 2026-08-17, TICKET-21). Две копии, одновременно опрашивающие одно устройство, дают достаточно устойчивого трафика, чтобы заклинить config-endpoint — это тот же конфликт, что с вендорским софтом, только полностью в нашей власти. Повторный запуск обязан поднимать уже открытое окно, а не открывать своё. Реализуется на уровне `app` (Tauri single-instance), не в `pcore`.
- **Stall останавливает и опрос тоже** (уточнено 2026-08-17, TICKET-21). Kill-switch из FR3 недостаточно понимать как «не повторять эту команду»: повторное открытие устройства не восстанавливает залипший endpoint, а любая дополнительная активность держит его в этом состоянии. Поэтому при stall'е прекращается вся работа с устройством, включая фоновое сканирование и обновление индикаторов, до физического переподключения. Следствие для FR11: состояние устройства доезжает до UI событиями; UI не имеет права инициировать обращение к устройству ради обновления индикатора.

## Out of scope

Идентично §1.3 плана + явно исключённые пункты §17.17–20 (firmware update/recovery, аналоговый вывод в ViGEm-геймпад, гарнитуры/DAC, мобильное/веб-хранилище профилей) — все помечены DEFERRED, не отклонены навсегда.

## Acceptance criteria

Соответствуют критериям успеха по фазам (§16 плана), адаптированным под принятые решения интервью:

- **AC1 (Phase 0 DoD).** Существует документ «карта мира» (prior-art инвентаризация), зафиксирована лицензия (ADR-0001, см. `docs/decisions/0001-license.md`), в наличии референсное устройство. **Изменено 2026-08-17 дважды:** (1) пункт «куплена ROYUAN-плата» снят — покупка отменена; (2) выяснилось, что EPOMAKER физически находится не у разработчика, а у стороннего владельца, поэтому она **не является референсным устройством** — reference board проекта — AULA Hero 84 HE, а EPOMAKER переведена в remote external validation track (TICKET-09/06). **Дополнено 2026-08-18:** локально появилось второе устройство другой категории — беспроводная мышь **VXE Dragonfly R1 SE+** с 2.4 ГГц ресивером; её read-only инвентарь снимается в TICKET-22 до проектирования реестра. Пункт «автору sharkfin отправлено сообщение» остаётся невыполненным осознанно (TICKET-02 отложен пользователем) и не блокирует последующие фазы.
- **AC2 (Phase 1 DoD).** При подключении AULA Hero 84 HE по USB приложение (а) корректно идентифицирует модель через `pregistry`-fingerprint, (б) показывает реальные значения actuation/RT, считанные с устройства в read-only режиме, (в) ни один опкод записи не исполним без `SafeCommandId`. Второе устройство в этом критерии не участвует: локально доступной второй платы у проекта нет (см. AC1).
- **AC3 (эксперимент Windows HID).** Разделён 2026-08-17 на две независимые части, поскольку второе устройство перестало быть локальным:

  **AC3a (TICKET-08, выполнен).** Зафиксирован полный HID-инвентарь AULA Hero 84 HE на Windows через `hidapi`, снятый продуктовым кодом транспорта (с прямым Win32 `CreateFile`/`HidD_*` как escape hatch внутри `ptransport`, если `hidapi` недостаточно — см. FR7): какие TLC открываются, какие дают `ERROR_ACCESS_DENIED`, доступен ли vendor-defined TLC с аналоговым стримом. Открытый вопрос об аналоговом TLC требует I/O и переходит в TICKET-12.

  **AC3b (TICKET-09, remote external validation).** Обычная пользовательская сборка Peripheral, запущенная **на чужом Windows-ПК без какого-либо dev-toolchain**, самостоятельно получает безопасный read-only инвентарь неизвестной EPOMAKER и экспортирует его в стандартный versioned-артефакт, структурно сопоставимый с инвентарём AULA; на его основе строится сравнительный отчёт двух устройств. Владельцу устройства не требуется ничего, кроме `скачать → запустить → подключить → Export`. Инвентарь снимается **тем же production-путём**, что и для AULA — vendor-specific ветка enumeration запрещена: если generic-транспорт не справился, чинится абстракция, а не создаётся частный случай. Сравнительный отчёт — реальный вход для многосигнального матчинга: он показывает, какие сигналы фактически различают устройства.

  Принадлежность второго устройства к какому-либо protocol family **не предполагается заранее** и не выводится из бренда: EPOMAKER — брендодержатель, а не производитель контроллера. Отсутствие доступного config-интерфейса — такой же валидный результат, как его наличие, и обязывает приложение сказать «config-интерфейс недоступен», а не пытаться писать наугад.
- **AC4 (Phase 2 DoD, за пределами этого планового прохода).** Слайдер actuation/RT реально меняет порог срабатывания, подтверждено аналоговым стримом, а не только ответом устройства.
- **AC5 (сквозной).** Ни одного подтверждённого случая порчи чужой платы записью приложения (метрика успеха §16 плана, применяется ко всем фазам).

## Open questions

Классификация по правилам ticket-autopilot (`BLOCKING` / `SAFE_DEFAULT` / `DEFERRED`), перенесена и уточнена из §17 исходного плана.

### Разрешено на интервью (более не открыто)

- Лицензия проекта → proprietary, GPL только как prior art (ADR-0001).
- Кооперация со sharkfin → независимая разработка + контакт с автором ради обмена знаниями, не кода.
- Позиционирование → HE-first в маркетинге, universal в архитектуре.
- Референсное железо → **AULA Hero 84 HE, единственная reference board.** **Изменено 2026-08-17 дважды:** покупка ROYUAN-платы отменена решением пользователя; затем выяснилось, что полноразмерная EPOMAKER находится не у разработчика, а у стороннего владельца — она перестала быть reference board и стала **remote external validation device** (TICKET-09 → TICKET-06). Её платформенная принадлежность по-прежнему устанавливается по данным, а не предполагается.

### BLOCKING (для конкретных будущих фаз — не блокируют Phase 0/1, зафиксированы как условие входа в соответствующую фазу)

- **Q1.** Лицензия для device-данных/`.heprofile` от сообщества (открытая база данных отдельно от закрытого кода приложения, вероятный CC0/аналог) — блокирует не Phase 0/1, а первый community-submission workflow (Phase 3/4). Решить до открытия публичного `Submit device`.
- **Q2.** У скольких целевых плат аналоговый стрим сидит в отдельном vendor-TLC (доступен на Windows) vs. внутри клавиатурной коллекции (недоступен)? Блокирует, будет ли Analog Monitor флагманской фичей v1 или fallback-фичей для части моделей. Решается эмпирически: первое наблюдение — TICKET-08 (у AULA **два** vendor-TLC, и какой из них аналоговый, из дескрипторов не следует — нужен I/O, TICKET-12); второе наблюдение придёт из remote-артефакта TICKET-09. Первое внешнее свидетельство (не наше железо, `origin: FromVendorJs`-класса): как минимум на одной реальной плате стрим сидит в отдельном vendor-интерфейсе и читается из user-space на Windows — см. `docs/prior-art/royuan.md`.
- **Q3** (добавлено 2026-08-17, пересматривалось дважды в тот же день; существенно изменено 2026-08-18). `dev.power.battery`/tray battery-индикация (FR12) не может быть верифицирована на AULA Hero 84 HE — она подключается только по USB. **Вопрос остаётся открытым дольше, чем предполагалось:** тип подключения EPOMAKER (USB / 2.4 ГГц / Bluetooth) неизвестен и устанавливается теперь не локально, а удалённо — в TICKET-09/06, то есть заметно позже. **EPOMAKER заранее беспроводной не считается.** Если позднее подтвердится, что у неё есть доступный wireless/receiver config path и battery-телеметрия, это даст реальное железо для `dev.connection`/`dev.power.battery`/`dev.power.charging`/Tray-UI раньше мышиной фазы. Если нет — исходная зависимость на будущую wireless-периферию (фаза 6) остаётся. Capability-модель в обоих случаях не меняется: `dev.power.*` уже корректно обобщён на любое wireless-устройство.

  **Изменение 2026-08-18: беспроводное устройство появилось локально.** VXE Dragonfly R1 SE+ подключается через 2.4 ГГц ресивер, то есть `dev.connection` впервые получает устройство, у которого это поле имеет более одного значения, а `dev.power.*` — потенциальное реальное железо для верификации, не дожидаясь фазы 6. Что именно из этого достижимо, устанавливает TICKET-22 наблюдением: **наличие стандартного battery HID usage** — предмет инвентаря. Вендорский путь к заряду (собственный опкод, запрос к ресиверу) потребовал бы probe и находится вне scope инвентаря; если такой путь обнаружится как очевидный и безопасный, он оформляется отдельным read-only тикетом, а не расширением TICKET-22. До результата TICKET-22 вопрос остаётся открытым — беспроводное подключение само по себе не означает читаемый заряд. Tray-*оболочка* (иконка, quick-панель, клик-поведение) не заблокирована ни в одном случае — может собираться на моке `BatteryState`.

### SAFE_DEFAULT (принят дефолт плана, можно поменять по мере данных)

- Формат реестра: YAML-источник → сгенерированный SQLite (не сразу SQLite) — ревьюабельные diff'ы в PR.
- Версионирование протоколов при изменении прошивки: quirk-оверрайды, пока их <5 на семейство; иначе — отдельная family.
- Фоновый daemon/tray для процесс-пресетов: тонкий opt-in tray-процесс, отдельно от GUI. **Требует пересмотра при декомпозиции TICKET-20** (добавлено 2026-08-17): раз System Tray (FR12) теперь штатная часть основного приложения (Tauri `TrayIcon` внутри того же процесса, не отдельный daemon), process watcher из §17.9 плана, возможно, разумнее вести в том же процессе, а не в отдельном тонком tray-процессе — решается на архитектурном чекпоинте перед TICKET-17/20, не сейчас.
- Конфликт с вендорским софтом: детектить и предупреждать, не захватывать силой.
- Формат key matrix/layout: KLE-совместимый импорт.
- Onboarding udev-правил на Linux: и пакет, и показ команды в UI.
- WebHID-сборка: делать, но после Phase 2 (не блокирует Phase 0/1 планирование).
- Монетизация: платное приложение (следует из решения о лицензии), донаты как дополнение — конкретная модель (одноразовая покупка / подписка) DEFERRED до момента, когда появится что продавать.
- Язык интерфейса: EN-first + RU локализация с первого релиза.
- Телеметрия: нет; вместо неё явная кнопка «отправить профиль устройства».
- Встроенные игровые пресеты: только шаблоны + импорт из community-репо, не гарантированно «правильные» настройки от проекта.

### DEFERRED (сознательно не решается в этом плановом проходе)

- Итоговый нейминг продукта (`Peripheral` vs альтернативы).
- Firmware update/recovery из bootloader — отдельный проект/expert-mode, не v1.
- Аналоговый вывод в ViGEm-геймпад.
- Гарнитуры/DAC/микрофоны — только структура папок.
- Мобильное/веб-хранилище профилей.

## Test seams

- **Приватность.** Автоматический тест, доказывающий, что ни один input-report из клавиатурной input-коллекции не попадает в Learning Mode capture-лог — для web- и desktop-сборки одинаково (FR8). Это прямое условие корректности claim'а в README про приватность (§5 плана, раздел WebHID).
- **Device emulator (`tools/emu`).** Подставной HID-девайс, воспроизводящий записанные ответы + умеющий «врать» как настоящий (повторять предыдущий ответ на неподдержанную команду) — единственный способ иметь CI без физического железа на раннере.
- **Replay-корпус.** Каждый принятый `.heprofile` от сообщества становится тест-кейсом «fingerprint → ожидаемое семейство».
- **Property-тесты кодеков.** `encode(decode(x)) == x`, checksum, границы диапазонов capability.
- **Fuzzing парсера report descriptor'ов** — вход из недоверенного источника (устройства).
- **Hardware-in-the-loop.** AULA Hero 84 HE и VXE Dragonfly R1 SE+ (добавлена 2026-08-18) на машине разработчика — ручной чеклист перед каждым релизом, затрагивающим протокольный слой. Мышь проходит его в каждом поддерживаемом режиме подключения: одно физическое устройство, видимое системой по-разному, — самый дешёвый способ поймать регресс в identity-модели. **Изменено 2026-08-17:** второго устройства на машине разработчика нет; EPOMAKER проходит тот же чеклист удалённо, обычной пользовательской сборкой у стороннего владельца (TICKET-09), и это ужесточает, а не ослабляет требование: путь должен работать без единого инструмента разработчика. Расхождение между устройствами является находкой о транспорте, а не поводом для отдельной ветки под устройство.
- **Redaction по построению** (добавлено 2026-08-17). Автоматический тест: артефакт, который приложение отдаёт пользователю на экспорт (device report / `.heprofile` / диагностический журнал), не содержит серийного номера устройства и прочих идентификаторов экземпляра — присутствует только факт их наличия (см. § Domain rules). Проверяется на артефакте, а не на коде, который его пишет: экспорт по построению безопасен для передачи третьему лицу.
- **Tray battery-selection logic (FR12).** Детерминированный unit-тест: набор `BatteryState` от N подключённых устройств → корректный выбор "наименьший заряд" для режима иконки по умолчанию; корректное поведение при 0 wireless-устройств (fallback на app-иконку, не крэш/не пустая иконка).
- **ACL/SafeCommandId compile-time seam.** Тест, подтверждающий, что ни один opcode с классом `destructive`/`unknown` не транслируется в валидный `SafeCommandId` при генерации из тестового реестра с намеренно «плохой» записью.
- **Диагностический журнал провода без полезной нагрузки** (добавлено 2026-08-17, TICKET-21). Кольцевой буфер последних обменов с устройством для диагностики stall'ов хранит только время, направление и опкод. Полезная нагрузка не хранится **никогда**: в ней бывает раскладка, а в раскладке — макросы с паролями, и этот журнал по построению предназначен для отправки пользователем в баг-репорт. Тест: сгенерировать обмен с известным байтовым паттерном в payload и убедиться, что паттерн не встречается в выводе журнала. Это третий приватный контур наряду с capture-логом Learning Mode (FR8) и журналом записей (FR3).
- **Согласованность дублирующихся артефактов** (добавлено 2026-08-17, TICKET-21). Автоматические проверки, что одно и то же знание не разъехалось по копиям: (а) каждый VID из реестра присутствует во всех копиях udev-правила (пакет + текст, показываемый в UI); (б) любое устройство из реестра попадает под сканирование по своему VID — иначе плата числится поддержанной, но не может быть найдена; (в) сгенерированные артефакты (список поддержки, SQLite из YAML) в CI перегенерируются и сборка падает при расхождении с закоммиченным; (г) права на запись выданы ровно тем семействам, что перечислены как известные. Основание: у prior art это правило разъезжалось дважды именно на udev-правилах (`docs/prior-art/sharkfin-methods.md`, метод 10).

⚠️ **Флаг, не блокер:** название токена «Real Madrid Gold» ссылается на бренд футбольного клуба Real Madrid. Сам HEX-код использовать можно свободно (цвет как таковой не является чьей-то интеллектуальной собственностью), но:
- имя токена — внутреннее (код/дизайн-система), **не выводить в публичный маркетинг, название продукта или App Store/сайт листинг** без юридической проверки на предмет ассоциации с чужим брендом (та же логика, что ADR-0001 применяет к именам устройств-брендов в §14 плана: описательное использование ок, ничего похожего на аффилиацию — нет);
- при публикации UI-kit/style guide переименовать токен во что-то нейтральное (`accent-gold`/`brand-gold` и т.п.) или явно снять вопрос с юристом, если сохранение референса к Real Madrid осознанно.
